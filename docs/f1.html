Endpoints

Tres roles: App, Worker y Admin. Cada key va en su propio header.

Crea un job con validación de payload. Infiere requirements por servicio si no se proveen. Valida SSRF en webhook_url. Emite NOTIFY jobs_channel para despertar workers en long-poll.

REQUEST

curl -X POST http://localhost:8080/ai/jobs \
  -H "X-App-Key: my-app-key" \
  -H "Content-Type: application/json" \
  -d '{
    "service": "transcription",
    "priority": "high",
    "payload": {
      "audio_url": "https://cdn.example.com/audio.mp3",
      "language": "es"
    },
    "webhook_url": "https://mi-app.com/callbacks/done"
  }'

RESPONSE 201

{
  "id": "a1b2c3d4",
  "service": "transcription",
  "status": "pending",
  "priority": 1,
  "requirements": { "min_vram_mb": 10000 },
  "routing": { "prefer": "local", "allow_external": false },
  "retry_count": 0,
  "max_retries": 3,
  "created_at": "2026-06-10T00:00:00Z"
}

VALIDACIONES

  • • service vacío → 422
  • • webhook_url con IP privada/Tailscale → 422 (RFC 1918, localhost, 100.64.0.0/10)
  • • webhook_url sin https:// → 422
  • • priority omitido → "normal" (5)
  • • requirements omitido → inferido por service

Mecanismos clave

Ledger de VRAM

El problema: varios workers comparten la misma GPU. Filtrar por métricas tiene hasta 10s de lag y dos claims simultáneos pueden ver la misma VRAM "libre". La solución: un UPDATE atómico que actúa como semáforo.

Demo interactiva

0 / 10,000 MB reservados
0%

El UPDATE atómico

-- Si no hay VRAM suficiente, no retorna fila
-- y el claim no se asigna (sin error, sin retry)
UPDATE gpus
SET vram_reserved_mb = vram_reserved_mb + $min_vram
WHERE id = $gpu_id
  AND vram_reserved_mb + $min_vram
      <= vram_total_mb - $margin
RETURNING id;
✓ Si retorna fila → VRAM reservada, job asignado
✗ Si no retorna fila → VRAM insuficiente, job sigue pending
⚡ Todo ocurre en la misma transacción con el SKIP LOCKED — atómico e imposible de sobre-reservar

Flujo del claim

4 pasos dentro de una única transacción PostgreSQL. Si cualquier paso falla, todo hace rollback.

1

Leer capabilities del worker

SELECT capabilities, gpu_id FROM workers WHERE id = $1

2

Seleccionar job elegible

WHERE status='pending' AND service = ANY($services)
ORDER BY priority, created_at
FOR UPDATE SKIP LOCKED LIMIT 1

3

Reservar VRAM atómicamente

UPDATE gpus SET vram_reserved_mb += $req
WHERE ... AND vram_reserved_mb + $req <= total - margin

4

Transicionar job a running

UPDATE jobs SET status='running', worker_id=$id, started_at=now()

Fencing — el worker zombie

Sin fencing, una caída de red de 90s produce doble ejecución y doble costo. El campo worker_id en el job actúa como token de propiedad.

Worker A clama el job

jobs.worker_id = "worker-A"

Worker A pierde red (90s)

Sigue ejecutando localmente, no puede hacer heartbeat

Monitor detecta timeout

Job → pending (worker_id = NULL), VRAM liberada, Worker A → offline

Worker B clama el mismo job

jobs.worker_id = "worker-B"

Worker A vuelve y reporta complete

WHERE id=$job AND worker_id="worker-A" → 0 filas afectadas

409 Conflict

EL UPDATE CON FENCING

UPDATE jobs
SET status = $1, result = $2, completed_at = now()
WHERE id = $job_id
  AND worker_id = $reporter_id  -- fencing
  AND status = 'running'
RETURNING id;

Si no retorna fila → el handler responde 409. El worker zombie descarta su resultado.

Retry con backoff exponencial

Fallos transitorios se recuperan solos. Fallos permanentes terminan en error sin loops infinitos.

LÓGICA EN CÓDIGO

// retry.go
func shouldRetry(retryCount, maxRetries int) bool {
    return retryCount < maxRetries
}

func nextRetryDelay(retryCount int) time.Duration {
    // 30s → 60s → 120s
    return time.Duration(30*(1<<retryCount)) * time.Second
}
⚠️

max_retries = 0

Error directo, sin reintentos. Para payloads inválidos o cancelaciones.

♻️

retry_after en el claim

El claim ignora jobs con retry_after > now(), respetando el backoff.

🛑

retry_count = max_retries

Próximo complete con error → status error definitivo, webhook disparado.
