## T4.5 ✅ Gestión de modelo: carga lazy + descarga por inactividad

**Fecha:** 2026-06-15

### Archivos modificados
- `workers/worker_whisper/__init__.py` — añade model manager: globals `_model`, `_model_lock`, `_active_jobs`, `_last_released`, `_worker_id`, `_unload_client`; funciones `_acquire_model()` (carga lazy + contador de jobs activos), `_release_model()` (decrementa contador + resetea idle clock), `_idle_watcher()` (daemon thread que comprueba cada 60s y descarga si `_active_jobs == 0` y han pasado ≥`_IDLE_TIMEOUT` segundos desde el último job). `execute()` envuelve la transcripción en `try/finally` para garantizar que `_release_model()` siempre se llama. `main()` inicializa `_worker_id` y `_unload_client` antes de arrancar el watcher y el scaffold.
- `workers/worker_base/api_client.py` — añade `unload_model(worker_id)`: `POST /workers/{id}/unload-model` con `X-Worker-Key`.
- `workers/tests/test_whisper_execute.py` — añade fixture `autouse _reset_model_state` (evita fuga de estado entre tests) + 9 tests nuevos de T4.5: `test_acquire_model_loads_when_none`, `test_acquire_model_reuses_cached`, `test_release_model_decrements_active_jobs`, `test_acquire_increments_release_decrements`, `test_execute_releases_model_on_success`, `test_execute_releases_model_on_transcription_error`, `test_execute_reloads_model_after_unload`, `test_idle_watcher_unloads_model_after_timeout`, `test_idle_watcher_skips_unload_when_active_job`, `test_idle_watcher_skips_unload_before_timeout`.

### Configuración por env vars
| Variable | Default | Descripción |
|---|---|---|
| `WHISPER_IDLE_TIMEOUT` | `600` | Segundos de inactividad antes de descargar el modelo |

### Notas
- El lock se mantiene durante la llamada HTTP a `unload-model` para prevenir una carrera TOCTOU: sin el lock, un nuevo job podría cargar el modelo entre el momento en que el watcher decide descargar y la notificación al ledger, dejando el ledger con VRAM = 0 mientras el modelo está cargado.
- Los criterios "VRAM sube al primer job" y "VRAM baja tras 10 min" quedan `[ ]`: requieren hardware real (ialab + agente reportando métricas).

## T4.8 ✅ Timeout máximo por job, configurable por service

**Fecha:** 2026-06-15

### Archivos modificados
- `api/internal/jobs/handler.go` — añade `serviceMaxDuration map[string]time.Duration` con duraciones por servicio (`transcription: 4h`, `llm_chat: 30m`, etc.); exporta `ServiceMaxDurations()` para que el monitor lo consuma sin conocer los valores concretos.
- `api/internal/jobs/store.go` — añade `FailTimedOutJobs(ctx, pool, maxDurations)`: itera por service, usa `FOR UPDATE SKIP LOCKED` (seguro ante llamadas concurrentes del monitor), llama `ReleaseVRAMReservation` y luego reencola o marca `error` según `retry_count < max_retries`. Delega en `failTimedOutJobsForService` (unexported) que maneja una transacción por service.
- `api/internal/monitor/monitor.go` — importa el paquete `jobs`; en `tick()` llama `jobs.FailTimedOutJobs(ctx, pool, jobs.ServiceMaxDurations())` tras el check de heartbeat; errores se loguean sin interrumpir el tick.
- `api/integration_test.go` — añade 4 tests (T4.8):
  - `TestJobTimeout_ExhaustedRetries` — job con `max_retries=0` pasado 2h → `error`.
  - `TestJobTimeout_SchedulesRetry` — job con `max_retries=2` pasado 2h → `pending` + `retry_after`.
  - `TestJobTimeout_WithinLimit_NotAffected` — job iniciado hace 5 min, límite 30 min → sigue `running`.
  - `TestJobTimeout_ReleasesVRAM` — verifica que `vram_reserved_mb` vuelve a 0 tras timeout.

### Notas
- El timeout usa `started_at < $cutoff` (tiempo absoluto calculado en Go), no un intervalo PostgreSQL, para evitar dependencia del formato de `time.Duration.String()`.
- Este timeout es distinto del heartbeat (90s): acota la duración total del job, no la ausencia de señal del worker.

## Riesgos y deuda técnica detectada

| Ítem | Severidad | Descripción |
|---|---|---|
| `vram_total_mb` placeholder en `.env.example` | Baja | El valor 24564 es ficticio; el valor real se mide y fija en T4.9. |
| Fencing basado en `status = 'running'` | Informativo | `RegisterFile` solo funciona mientras el job está `running`. Si el worker llama `upload_file_metadata` después de `complete`, recibirá 409 (fencing). Esto es correcto: los archivos deben registrarse antes de completar el job. |
| Python 3.12 en Dockerfile.whisper via deadsnakes | Baja | `add-apt-repository ppa:deadsnakes/ppa` agrega latencia al build y tiene una dependencia de terceros. Alternativa: imagen `python:3.12-slim` + instalar CUDA libs aparte (más limpio, evaluable en T4.4). |
