## T6.1 ✅ Tooling de deploy a ialab: target `rsync` + guarda de disco + `--force-recreate`

**Fecha:** 2026-06-17

### Archivos creados
- `deploy/ialab/deploy-workers.sh` — script que corre ON ialab tras el rsync: (1) guarda de disco sobre el docker root antes del build, aborta con mensaje claro si hay menos de `DISK_MIN_GB` (default 5 G); (2) `docker compose up --build -d --force-recreate` para todos los workers; (3) muestra `docker compose ps` como confirmación local. Diferencia clave respecto a un `restart`: fuerza la recreación del contenedor y la re-lectura del `env_file`.
- `deploy/ialab/verify-workers.sh` — script que corre LOCALMENTE tras el deploy: (1) espera 8 s para que los workers se registren; (2) SSHea a ialab para `docker compose ps` y grepa los logs por líneas de registro/polling; (3) si `ADMIN_API_KEY` está en `.env.deploy`, llama a `GET /admin/workers` en el VPS y muestra el `status` de cada worker — la verificación definitiva según el criterio de aceptación.

### Archivos modificados
- `Makefile` — añade variables `IALAB_USER`, `IALAB_HOST`, `IALAB_DIR`, `DISK_MIN_GB`, `VPS_API_URL`; target `deploy-ialab` (rsync → deploy-workers.sh → verify-workers.sh, todo sin pasos manuales fuera del Makefile); target `verify-ialab` (solo la verificación, sin redeploy); ambos añadidos a `.PHONY`.
- `docs/IALAB.md` — nueva sección "Deploy desde local" con tabla de variables de `.env.deploy`; sección "Redeploy de workers — `--force-recreate`, no `restart`" que codifica la regla que F4/F4.5 dejaron sin documentar (R5); sección "Rutas de env files de workers" que aclara el orden de carga (`/etc/` vs `~/.config/`) y cómo verificar el env real del proceso (no del archivo).

### Notas
- El check de disco se ejecuta en ialab (sobre el docker root), no en local: lo que importa es el espacio donde Docker va a hacer el build/pull.
- La verificación vía VPS API (`ADMIN_API_KEY`) es opcional pero es el check definitivo del criterio "registrado y claimando". Sin la key, la verificación cae back a logs (útil en CI o sin acceso a la key).
- `workers-build`, `workers-up`, `workers-down` ya existían en el Makefile como targets para correr desde ialab directamente; `deploy-ialab` es el target para correr desde local. No se eliminaron los anteriores — siguen válidos para sesiones SSH interactivas.
- Deuda técnica visible: los targets `workers-*` en el Makefile asumen que se corren desde ialab (sin SSH); un operador que los llame desde local va a fallar. No se toca en T6.1 (no relacionado con la tarea).

## T6.2 ✅ Timebox de modelo de traducción

**Fecha:** 2026-06-18

### Archivos creados
- `deploy/ialab/timebox-model.sh` — script que corre ON ialab para evaluar un modelo candidato: verifica que Ollama responde, hace pull del modelo, ejecuta 5 traducciones de prueba (3 ES→EN + 2 EN→ES del estilo corpus Video Crack), mide VRAM antes/después con `nvidia-smi`, e imprime el `ollama list` con el ID del modelo para copiarlo como digest de pinning. El resultado se pega en `docs/RUNBOOKS/t6.2-model-timebox.md`.
- `docs/RUNBOOKS/t6.2-model-timebox.md` — runbook con tabla de candidatos, plantilla de resultados (VRAM medida, tiempos de inferencia, calidad por muestra, veredicto), y pasos post-decisión (cómo actualizar el compose con el digest y ejecutar `pull-model.sh`).

### Resultados reales (ialab, 2026-06-18)
- **Modelo elegido:** `qwen2.5:7b` · Q4_K_M · 7.6B params · 4.7 GB en disco
- **Digest:** `845dbda0ea48ed749caafd9e6037047aa19acfcfd82e704d7ca97d631a0b697e`
- **VRAM pico:** 4779 MiB (baseline 346 MiB → loaded 5125 MiB)
- **Latencia warm:** ~260–300 ms/subtítulo; cold load ~27 s (carga del modelo en GPU)
- **Calidad:** `aceptable` en las 5 pruebas ES↔EN (sentido correcto, sin alucinaciones)
- Solo se evaluó un candidato porque los resultados fueron inmediatamente buenos; no fue necesario `llama3.1:8b`.
- **Insumo para T6.6:** `serviceRequirements["translation"] = 4000` queda por debajo del pico real (4779 MiB); ajustar en T6.6.
- **Convivencia (adelanto T6.9):** whisper (~5060 MiB pico real) + qwen2.5:7b (~4779 MiB) = ~9839 MiB sobre 15946 MiB. Margen ~6107 MiB — cómodo.

## T6.3 ✅ Ollama en ialab (contenedor, modelo pinneado, bind correcto)

**Fecha:** 2026-06-18

### Archivos creados
- `deploy/ialab/pull-model.sh` — script que corre ON ialab para hacer pull del modelo elegido en T6.2 hacia el servicio Ollama. Acepta el spec de modelo con digest (`nombre@sha256:...`) para pull pinneado. Ejecutar una vez tras el primer `make deploy-ialab` que incluye el servicio ollama; el modelo queda en el volumen `ollama_models` y sobrevive recreaciones.

### Archivos modificados
- `deploy/ialab/docker-compose.yml` — añade el servicio `ollama` y el volumen `ollama_models`. El servicio usa `network_mode: host`, `restart: unless-stopped`, `OLLAMA_HOST=127.0.0.1:11434` en `environment:` (restricto a localhost — worker-ollama lo alcanza desde el mismo host), y GPU reservation (mismo patrón que worker-whisper). La imagen es `ollama/ollama:latest` con un TODO comentado para reemplazar con el digest de T6.2 una vez ejecutado el timebox.

### Notas
- `OLLAMA_HOST=127.0.0.1:11434` restringe Ollama a localhost. Con `network_mode: host`, el `worker-ollama` lo alcanza en `127.0.0.1:11434` sin exponer Ollama a la red Tailscale ni a internet. Decisión deliberada de seguridad.
- Imagen pinneada en compose: `ollama/ollama@sha256:bfc9c6d5...`. Modelo `qwen2.5:7b` en volumen `ollama_models`; sobrevive `--force-recreate` sin re-descarga.
- Smoke test ejecutado en ialab: `curl .../api/generate` → `"Hello world"` en 300 ms (warm). Criterio 2 verificado.
- La imagen actual del compose (`ollama/ollama:latest` → reemplazada por digest tras T6.2) ya estaba descargada en ialab desde el primer deploy, por lo que el re-deploy con el digest fue instantáneo (no re-pull).

## T6.4 ✅ `worker-ollama` sobre el scaffold: `translation` + `llm_chat`

- `workers/worker_ollama/__main__.py` — entry point (`from worker_ollama import main; main()`).

### Archivos modificados
- `workers/pyproject.toml` — agrega `worker-ollama = "worker_ollama:main"` en `[project.scripts]`.

### Configuración por env vars
| Variable | Default | Descripción |
|---|---|---|
| `OLLAMA_HOST` | `http://127.0.0.1:11434` | URL base del servicio Ollama en ialab |
| `OLLAMA_MODEL` | `qwen2.5:7b` | Modelo a usar (debe coincidir con el pinneado en T6.3) |
| `OLLAMA_IDLE_TIMEOUT` | `600` | Segundos de inactividad antes de liberar VRAM en el ledger |

### Notas
- El gestor de modelo usa `_model_loaded: bool` en lugar del objeto de modelo de whisper — no hay objeto Python que retener; Ollama gestiona la GPU internamente.
- El idle watcher hace dos cosas: (1) llama a `POST /workers/{id}/unload-model` para liberar la reserva de VRAM en el ledger de la plataforma; (2) llama a Ollama con `keep_alive=0` para que evicte el modelo de GPU. Si solo se hace (1), el ledger cree que la VRAM está libre pero Ollama sigue ocupándola.
- El criterio "verificable en T6.9" (que `vram_reserved_mb` baje en ialab real) se deja `[ ]` — requiere hardware real y dos modelos cargados simultáneamente.
- Fencing (409): lo maneja el scaffold sin código nuevo en el worker.

## T6.6 ✅ Calibrar `min_vram_mb` real de `translation`/`llm_chat`

**Fecha:** 2026-06-17

### Archivos modificados
- `api/internal/jobs/handler.go` — `serviceRequirements["translation"]` y `["llm_chat"]` actualizados de 4000 a **5300 MiB** (pico real medido en T6.2: 4779 MiB + margen 521 MiB ≈ 11%); `init()` extendido con `MIN_VRAM_TRANSLATION_MB` y `MIN_VRAM_LLM_CHAT_MB` (mismo patrón que `MIN_VRAM_TRANSCRIPTION_MB` de T4.9) para permitir ajuste sin redeploy de código si T6.9 revela picos distintos bajo carga real.

### Configuración por env vars
| Variable | Default | Descripción |
|---|---|---|
| `MIN_VRAM_TRANSLATION_MB` | `5300` | Override del requisito de VRAM para `translation` |
| `MIN_VRAM_LLM_CHAT_MB` | `5300` | Override del requisito de VRAM para `llm_chat` |

### Notas
- **Base de calibración:** T6.2 midió pico 4779 MiB para `qwen2.5:7b` con `nvidia-smi` durante inferencia real en ialab.
- **Margen:** 521 MiB (≈11%). Referencia: whisper en producción real tiene margen de 440 MiB (5500 − 5060 MiB). Mismo orden de magnitud.
- `translation` y `llm_chat` usan el mismo modelo; mismo valor de reserva. El ledger los trata como jobs separados — si ambos se encolan a la vez, cada uno reserva 5300 MiB. La convivencia real (whisper + ollama) se valida en T6.9.
- No se requiere migración de schema: es cambio de constante + env.

## T6.7 ✅ Video Crack adopta traducción detrás de flag (`legacy` / `platform` / `both`)

**Fecha:** 2026-06-17

### Archivos modificados
- `video-crack/backend/routers/tradu.py` — añade `TRANSLATE_MODE = os.getenv("TRANSLATE_MODE", "both")` junto a `TRANSCRIBE_MODE`; añade funciones `_translate_via_platform()` y `_submit_translation_background()`; modifica el bucle de traducción para respetar el flag de tres posiciones. Con `TRANSLATE_MODE=platform`, no se carga LM Studio (`_load_lms` / `_unload_lms` se saltan).

### Configuración por env vars
| Variable | Default | Descripción |
|---|---|---|
| `TRANSLATE_MODE` | `both` | `legacy` = solo LM Studio local; `platform` = solo plataforma; `both` = legacy + plataforma en background |

### Notas
- El payload al worker usa el mismo formato numerado del legacy (`"1. texto\n2. texto\n..."`), lo que permite reutilizar el parser de respuesta existente y es compatible con el prompt actual de `worker-ollama`.
- En modo `both`, la tradución de plataforma corre en un thread daemon y guarda `subtitles.{lang}.platform.vtt` para el comparador de T6.8. Errores del background no abortan el job principal.
- Se reutiliza `PLATFORM_API_URL`, `PLATFORM_APP_KEY` y `PLATFORM_JOB_TIMEOUT` ya existentes (T4.5.5); no se crea nueva identidad ni nueva app key.
- **Criterios `[ ]`**: todos dependen de `worker-ollama` desplegado en ialab y stack completo. Se verificarán en T6.9/T6.10.
