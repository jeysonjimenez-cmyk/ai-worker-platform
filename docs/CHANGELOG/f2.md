## T2.1 — `gpu_id` explícito en el registro de workers ✅ 2026-06-10

**Archivos modificados:**
- `api/internal/workers/store.go` — `RegisterParams` gana `GPUID *string`; `Register` usa ese valor si está presente, cae en `hostname+"/gpu-0"` si no
- `api/internal/workers/handler.go` — `registerRequest` gana `gpu_id omitempty`; se pasa a `RegisterParams`
- `api/cmd/worker-sim/main.go` — declara `"gpu_id": "sim-host/gpu-0"` explícitamente en el payload de registro
- `api/integration_test.go` — `TestWorkerRegister_ExplicitGPUID`: verifica que el id declarado llega a `gpus`, que no pisa `hostname/gpu-0`, y que re-registro no resetea `vram_reserved_mb`

**Riesgos / deuda:**
Ninguno. Fallback `hostname+"/gpu-0"` intacto — todos los tests de F1 siguen pasando sin cambios.

## T2.3 — Endpoint de ingesta de métricas en la API ✅ 2026-06-10

**Archivos modificados:**
- `api/internal/workers/store.go` — `MetricSample` struct + `IngestMetrics(ctx, pool, workerID, []MetricSample)`
- `api/internal/workers/handler.go` — `metricsRequest` struct + `Handler.IngestMetrics` + import `fmt`
- `api/main.go` — ruta `POST /workers/{id}/metrics` bajo `workerMW`
- `api/integration_test.go` — ruta en `buildServer` + 6 tests de integración contra PostgreSQL real:
  - `TestIngestMetrics_Single` — campos y timestamp de captura correctos
  - `TestIngestMetrics_Batch` — N muestras → N filas
  - `TestIngestMetrics_MissingRecordedAt` — 422 sin `recorded_at`
  - `TestIngestMetrics_WrongWorker` — 403 path/auth mismatch
  - `TestIngestMetrics_NoWorkerKey` — 401 sin key o con key de app
  - `TestIngestMetrics_NoGPUFields` — GPU fields null en nodos sin GPU

**Riesgos / deuda:**
- Insert en loop individual dentro de transacción — suficiente para el caso de uso (buffers de decenas de muestras). Si el buffer crece a miles, considerar `pgx.CopyFrom`.
- Sin límite de tamaño de batch — no es un problema real con el agente (buffer acotado en T2.7), pero a tener en cuenta si el endpoint se expone a más clientes.

## T2.4 — Scaffold del Node Agent + lectura de métricas ✅ 2026-06-11

**Archivos creados/modificados:**
- `agent/pyproject.toml` — `nvidia-ml-py`, `psutil`, `pytest`, `ruff`; dependencias congeladas
- `agent/uv.lock` — lock file generado
- `agent/agent/__init__.py`
- `agent/agent/config.py` — `Config` dataclass + `load()` desde env vars (`AGENT_API_URL`, `AGENT_API_KEY`, `AGENT_WORKER_ID`, `AGENT_INTERVAL_SEC`)
- `agent/agent/collector.py` — `MetricSample` dataclass + `collect()` + `_read_gpu()`; GPU fields `None` si pynvml no disponible
- `agent/tests/__init__.py`
- `agent/tests/test_collector.py` — 10 tests unitarios con pynvml mockeado (6 con GPU, 4 sin GPU)
- `.github/workflows/ci.yml` — nuevo job `agent` (ruff + pytest)
- `Makefile` — `build`, `test`, `lint` incluyen `agent/`

**Riesgos / deuda:**
- `pynvml` PyPI está deprecado; se usa `nvidia-ml-py` (mismo namespace `import pynvml`, paquete oficial NVIDIA).
- `nvmlInit()`/`nvmlShutdown()` por llamada es correcto para collect puntual. Cuando T2.7 agregue el loop, puede mantenerse el handle abierto — cambio de dos líneas.
- Criterio "valores coinciden con `nvidia-smi`" requiere verificación manual en ialab (no automatizable sin hardware real). Pendiente en T2.9.
