## T2.7 — Loop de reporte con buffer y reintentos ✅ 2026-06-11

**Archivos creados/modificados:**
- `agent/agent/reporter.py` — `Reporter` con buffer `deque(maxlen=N)` (drop-oldest automático), `flush()` con backoff exponencial (5 s → 5 min), `run_loop()` inyectable para tests
- `agent/agent/main.py` — entry point: conecta config → registro → `MetricsServer` → `Reporter` → loop
- `agent/tests/test_reporter.py` — 21 tests: buffer cap, flush success/failure, backoff, run_loop con collect_fn inyectado

**Decisiones de diseño:**
- Buffer con `collections.deque(maxlen=N)`: drop-oldest automático sin código extra.
- Backoff exponencial desde 5 s hasta 5 min; se resetea a cero tras flush exitoso.
- `run_loop` acepta `collect_fn` inyectado para ser testeable sin GPU ni red.
- `main.py` no se testea directamente — es el pegamento de módulos ya testeados individualmente.

**Riesgos / deuda:**
- Loop single-threaded: si `collect()` bloquea (lentitud de pynvml en ciertos estados del driver), el intervalo de 10 s se desfasa. No es problema para F2; en F3+ podría justificar un thread separado.
- Sin manejo explícito de `KeyboardInterrupt`/`SIGTERM` en `main.py` — el OS mata el proceso limpiamente y systemd (T2.8) gestiona el restart. Si se necesita graceful shutdown, se añade en ese punto.

## T2.10 — Alerta de deriva ledger ↔ VRAM real ✅ 2026-06-11

**Archivos modificados:**
- `api/internal/config/config.go` — nuevo campo `VRAMDriftMarginMB`; lee `VRAM_DRIFT_MARGIN_MB` (default 512 MB)
- `api/internal/workers/store.go` — `vramDriftExceeded(ledgerFreeMB, reportedFreeMB, marginMB int) bool` (función pura, testeable); `checkVRAMDrift` (best-effort: join `workers`→`gpus`, log warning si delta > margen, silencio si el worker no tiene GPU); `IngestMetrics` recibe `driftMarginMB int` y llama `checkVRAMDrift` tras commit
- `api/internal/workers/handler.go` — `Handler` gana campo `vramDriftMarginMB`; `NewHandler` acepta segundo parámetro entero; `IngestMetrics` lo pasa al store
- `api/main.go` — pasa `cfg.VRAMDriftMarginMB` a `NewHandler`
- `api/integration_test.go` — `buildServer` actualizado a `NewHandler(pool, 0, 0)`
- `api/internal/workers/drift_test.go` — **Nuevo** — 8 casos unitarios para `vramDriftExceeded`: dentro del margen, en el límite exacto, un MB sobre el margen, delta inverso, margen cero

**Riesgos / deuda:**
- El check toma el sample más reciente del batch con `vram_free_mb` no nulo. Para buffers acumulados de varios minutos, ese sample puede ser más antiguo que el estado actual del ledger — ruido aceptable dado que el propósito es detectar deriva sostenida, no picos momentáneos.
- `checkVRAMDrift` es best-effort (silencio total en error de DB o worker sin GPU): correcto para un warning de observabilidad, pero implica que si la join falla silenciosamente en producción, el log no aparecerá. Sin impacto funcional.

## T2.11 — Job de retención de `worker_metrics` ✅ 2026-06-11

**Archivos creados/modificados:**
- `migrations/0003_worker_metrics_hourly.up.sql` — tabla `worker_metrics_hourly` con PK `(worker_id, hour)`: avg/max de todos los campos numéricos, `vram_free_min` (peor caso de la hora), `sample_count`
- `migrations/0003_worker_metrics_hourly.down.sql` — rollback
- `api/internal/retention/retention.go` — **Nuevo paquete** — `Compact(ctx, pool)` exportada: agrega filas `> 7 días` con `INSERT … ON CONFLICT DO NOTHING` + `DELETE` en la misma transacción; `Run(ctx, pool)` con tick de 24 h (mismo patrón que `monitor`)
- `api/main.go` — `go retention.Run(ctx, pool)` junto a `monitor.Run`
- `api/integration_test.go` — tabla `worker_metrics_hourly` en `applyMigrations`; 4 tests de integración contra PostgreSQL real:
  - `TestRetentionCompact_OldRowsAggregated` — filas viejas compactadas, recientes intactas, `sample_count` correcto
  - `TestRetentionCompact_Idempotent` — segunda ejecución no duplica agregados ni errora
  - `TestRetentionCompact_MultipleHours` — 3 horas distintas → 3 filas en `worker_metrics_hourly`
  - `TestRetentionCompact_NothingToDo` — datos solo recientes → sin agregados, sin borrados

**Decisiones de diseño:**
- `ON CONFLICT (worker_id, hour) DO NOTHING` es la clave de idempotencia: si el proceso se cae tras el INSERT pero antes del DELETE, la segunda ejecución salta el INSERT y completa el DELETE.
- `DELETE` borra todas las filas antes de la fecha de corte de una vez, sin sub-select: el invariante es que si hay un agregado ya existente (de una ejecución anterior o de la presente), borrar las filas crudas es siempre correcto.
- `vram_free_min` en lugar de `vram_free_avg` como campo secundario: el mínimo de VRAM libre durante la hora es el dato más útil para diagnosticar presión de memoria.

**Riesgos / deuda:**
- El job corre cada 24 h y no hace la primera ejecución al arrancar — si la API ha estado caída días, la primera compactación se produce en el siguiente tick. No es un problema operativo, pero si se necesita backfill inmediato al arrancar se puede añadir una llamada inicial en `Run`.
- La transacción `Compact` puede ser larga si hay semanas de datos acumulados tras una caída prolongada de la API. Para el caso de uso previsto (un worker, ~8640 filas/día) esto no es un problema.
