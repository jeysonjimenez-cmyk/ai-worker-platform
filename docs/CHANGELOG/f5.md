## T5.5 ✅ Vista única: workers + jobs por estado, polling cada 5s

**Fecha:** 2026-06-15

### Archivos modificados
- `dashboard/src/App.jsx` — reemplaza el placeholder `Dashboard` con la vista real: componente `WorkersPanel` (tabla de workers con hostname, gpu_id, estado coloreado, job en curso y último heartbeat) y `JobsPanel` (tabla de jobs con filtro por estado mediante botones de tab; `pending/running/done/error/cancelled/Todos`). El `Dashboard` orquesta ambos con `useCallback`/`useEffect` + `setInterval(fetchData, 5000)` para polling cada 5s. Al cambiar el filtro de estado, se anula la selección activa de job. `StatusBadge` centraliza el coloreado de estados para workers y jobs.

### Notas
- El polling se implementa con `setInterval` dentro de `useEffect`; el cleanup cancela el intervalo al desmontar o cuando cambia `fetchData` (que depende de `statusFilter`). Esto garantiza que el filtro activo siempre se respeta en el próximo tick.
- El criterio "offline en <90s sin refrescar manualmente" queda `[ ]`: depende de que el monitor de heartbeat del API (F1) marque al worker como offline; la UI lo reflejará automáticamente en el siguiente tick de 5s, pero la verificación end-to-end requiere hardware vivo (T5.8).

## T5.8 — Fix: CORS bloqueaba el dashboard en navegador real

**Fecha:** 2026-06-16

### Contexto
El usuario probó el dashboard desde un navegador real (`http://100.106.192.45:3000`) y la llamada a `http://100.106.192.45:8081/admin/jobs` falló con: `No 'Access-Control-Allow-Origin' header is present on the requested resource`. Exactamente el gap que T5.8 había marcado como no verificado ("Verificación visual en navegador no ejecutada") — la verificación con `curl` no dispara preflight CORS (es un mecanismo solo de navegador), así que el bug era invisible a la verificación previa.

### Archivos modificados
- `api/main.go` — añade middleware `withAdminCORS` que envuelve **todo el mux** (no handlers individuales): para rutas `/admin/*` setea `Access-Control-Allow-Origin: *`, `Access-Control-Allow-Methods: GET, POST, OPTIONS`, `Access-Control-Allow-Headers: X-Admin-Key, Content-Type`, y responde 204 a `OPTIONS` sin requerir auth (el navegador manda el preflight antes de adjuntar `X-Admin-Key`). Cambia `Handler: mux` → `Handler: withAdminCORS(mux)` en el `http.Server`.
- `api/integration_test.go` — `buildServer` envuelve con `withAdminCORS(mux)` también; añade test `TestAdmin_CORS_PreflightAndHeaders` (preflight `OPTIONS /admin/jobs` → 204 con headers correctos sin auth; `GET /admin/jobs` autenticado también lleva `Access-Control-Allow-Origin`; rutas no-admin como `/ai/jobs/{id}` no llevan headers CORS). Duplica `withAdminCORS` en el archivo (convención ya existente: `package main_test` no puede importar símbolos no exportados de `package main`, igual que `buildServer` ya duplica la tabla de rutas).

### Por qué envolver el mux completo
Go 1.22+ `http.ServeMux` devuelve 405 automáticamente para `OPTIONS` sobre un patrón registrado solo con `GET`/`POST`, antes de que corra cualquier middleware atado al handler. El CORS tenía que interceptarse antes del routing del mux, no dentro de cada handler.

### Por qué `Access-Control-Allow-Origin: *` es seguro aquí
La auth de `/admin/*` es por header (`X-Admin-Key`), no por cookies — no hay modo "credentials" del navegador en juego, así que no hay riesgo de CSRF vía origen arbitrario leyendo una sesión de cookies ajena.

### Verificación
- `go test ./...` completo: sin regresiones.
- Desplegado a producción con `make deploy`; verificado en vivo:
  ```bash
  curl -i -X OPTIONS http://100.106.192.45:8081/admin/jobs \
    -H "Origin: http://100.106.192.45:3000" \
    -H "Access-Control-Request-Method: GET" \
    -H "Access-Control-Request-Headers: X-Admin-Key"
  # → 204, Access-Control-Allow-Origin: *
  ```

### Notas
- Este bug confirma por qué T5.8 había dejado los criterios "desde la UI" sin marcar pese a que el contrato API estaba 100% verificado: la verificación por `curl` no puede detectar fallos de CORS. Queda como lección para `docs/RUNBOOKS/`: cualquier verificación de un endpoint consumido por navegador debe incluir al menos un preflight `OPTIONS` con `Origin`, no solo el request real.
- Pendiente: confirmación del usuario de que el dashboard ahora carga sin el error de consola.
