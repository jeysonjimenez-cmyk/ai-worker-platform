## T3.3 — Heartbeat en thread separado del loop de inferencia ✅ 2026-06-13

**Archivos modificados:**
- `workers/worker_base/scaffold.py` — `Scaffold._heartbeat_loop()`: daemon thread dedicado; usa `threading.Event.wait(interval)` — espera el intervalo O hasta que `_stop` se active, lo que permita shutdown limpio sin esperar el próximo tick; errores individuales (red caída, timeout) se logean y se reintenta en el siguiente intervalo sin terminar el thread
- `workers/tests/test_scaffold.py` — `test_heartbeat_fires_while_execute_blocked`: verifica que ≥2 heartbeats llegan mientras `execute()` duerme 2.5s con intervalo de 1s; `test_heartbeat_survives_individual_failure`: el primer heartbeat lanza excepción y el segundo llega correctamente

**Riesgos / deuda:**
- El thread de heartbeat es `daemon=True`: si el proceso principal termina abruptamente (ej. `kill -9`), el thread muere con él sin enviar un heartbeat final. Es el comportamiento correcto — el heartbeat monitor del servidor (90s timeout) maneja el caso de worker caído.
- No hay backoff en fallos consecutivos del heartbeat: si el VPS está caído, el thread intenta cada `heartbeat_interval` segundos. Con el default de 10s esto genera ~6 logs de warning por minuto — ruido aceptable para un outage del VPS.

## T3.4 — Claim loop con long-poll y backoff ✅ 2026-06-13

**Archivos modificados:**
- `workers/worker_base/scaffold.py` — `Scaffold._run_claim_loop()`:
  - Long-poll: `POST /workers/{id}/claim?wait=N` con `timeout=N+10` en httpx
  - 200 → parse job, llama `execute()`, reporta resultado vía `_complete_job()`
  - 204 → sin job disponible, `_stop.wait(2)` antes de reintentar (el long-poll ya esperó)
  - Error de red → log warning + backoff exponencial (`1s → 2s → … → backoff_max`); backoff se resetea con cualquier respuesta HTTP exitosa
  - Error inesperado (4xx/5xx) → log error + `_stop.wait(5)` antes de reintentar
  - Si `execute()` lanza excepción → el job se completa con `error=str(exc)`, el worker sigue vivo
- `workers/tests/test_scaffold.py` — `test_claim_loop_calls_execute_and_complete`: verifica claim → execute → complete end-to-end; `test_claim_loop_retries_on_network_error`: primer claim lanza excepción, segundo claim funciona; `test_execute_error_reported_as_complete_error`: execute lanza ValueError → complete recibe `error=` con el mensaje

**Riesgos / deuda:**
- `poll_wait=0` en tests (sin long-poll) para que los tests no tarden 30s. En producción el default es 30s — importante que no se olvide setear `WORKER_POLL_WAIT` en el entorno si se quiere long-poll real.
- El backoff no diferencia entre errores transitorios (red caída) y errores permanentes (worker no registrado, key inválida). En el segundo caso el worker reintenta indefinidamente. Mitigación: el registro al arrancar falla rápido, así que si se llega al claim loop las credenciales ya están validadas.

## T3.8 — Graceful shutdown ante SIGTERM ✅ 2026-06-13

**Archivos modificados:**
- `workers/worker_base/scaffold.py` — `Scaffold.run()` instala `signal.signal(signal.SIGTERM, _sigterm)` antes de arrancar el heartbeat thread; `_sigterm` llama `self._stop.set()`; el job en curso termina normalmente (`_run_claim_loop` respeta `_stop` solo entre iteraciones, no interrumpe `execute()`); el heartbeat monitor del servidor re-encola el job en ≤90s si el job estaba en curso al momento del SIGTERM y el worker sale antes de completarlo
- `workers/tests/test_scaffold.py` — añadidos 2 tests:
  - `test_sigterm_stops_worker_with_no_job`: SIGTERM cuando idle → `_stop.is_set()` tras `run()`
  - `test_sigterm_stops_worker_during_execute`: SIGTERM con execute en curso → execute completa, worker sale limpio

**Decisión de diseño (ajuste del backlog):** No existe endpoint de "return to pending" en la API — la única forma de re-encolar es el timeout del heartbeat monitor (90s). Por lo tanto SIGTERM simplemente detiene el heartbeat y el claim loop; si hay un job en curso y execute no termina a tiempo, el heartbeat monitor lo re-encola. Este comportamiento es idéntico al que verifica T3.12 al matar el contenedor mid-job.

**Riesgos / deuda:**
- Si `execute()` tarda >90s tras el SIGTERM (y por tanto no envía heartbeat), el job se re-encola y potencialmente dos workers lo procesan en paralelo brevemente — el fencing del servidor (409) lo resuelve. No hay OOM ni corrupción de datos.
- `signal.signal()` solo funciona desde el hilo principal. Como `run()` se llama desde el main thread (comportamiento normal), esto es correcto. Un test que llame `run()` desde un thread auxiliar no puede recibir SIGTERM — los tests de T3.8 usan `os.kill(os.getpid(), signal.SIGTERM)` desde el main thread.

## T3.10 — Dockerfile base + entrada en Docker Compose de ialab ✅ 2026-06-13

**Archivos creados/modificados:**
- `workers/Dockerfile` — imagen base `python:3.12-slim` + uv 0.7.12 (pinned); `uv sync --frozen --no-dev` en layer cacheada; `PATH` apunta al venv para evitar re-sync de uv en runtime; CMD: `python -m worker_echo`
- `workers/worker_echo/__main__.py` — entry point de módulo para `python -m worker_echo` (sin build backend necesario)
- `workers/pyproject.toml` — sin cambios de producción (se probó `tool.uv.package = true` pero requiere build backend; revertido en favor de `__main__.py`)
- `deploy/ialab/docker-compose.yml` — servicio `worker-echo`: contexto `../../workers`, `network_mode: host` para acceder a Tailscale, env_file `/etc/ai-platform/worker-echo.env` con `required: false` (validación delega a `from_env()` del scaffold)
- `deploy/ialab/worker-echo.env.example` — plantilla de variables requeridas: `WORKER_API_URL`, `WORKER_KEY`, `WORKER_ADMIN_KEY`, `WORKER_ID`, `WORKER_CAPABILITIES`
- `Makefile` — targets: `workers-build` (build local para CI), `workers-up`, `workers-down`, `workers-logs`

**Criterios de aceptación:**
- `docker compose build` produce la imagen con dependencias congeladas ✅ (verificado localmente — build exitoso, 7 paquetes instalados desde uv.lock)
- Las credenciales y la URL llegan por entorno, no hardcodeadas en la imagen ✅ (`RuntimeError: required env var 'WORKER_API_URL' is not set` al intentar arrancar sin vars — comportamiento correcto)
- `docker compose up` arranca `worker-echo` en ialab y se registra contra la API del VPS vía Tailscale — verificable solo en ialab (criterio de T3.12)

**Decisiones de diseño:**
- `network_mode: host` en lugar de una red bridge con MACVLAN: es la forma más simple de dar al contenedor acceso a la interfaz Tailscale (`tailscale0`) de ialab, sin configuración adicional de redes en Docker. Los workers de F3 no necesitan aislamiento de red entre sí.
- `uv` solo en build-time; runtime usa el venv directamente vía `PATH`. Evita que `uv run` resincronice dependencias (incluidas dev) al arrancar el contenedor.
- `required: false` en env_file: `docker compose build` funciona sin el archivo de credenciales; el scaffold falla al arrancar si faltan vars requeridas (mensaje de error claro).

**Riesgos / deuda:**
- La versión de uv en el Dockerfile (`0.7.12`) está pinneada — actualizar intencionalmente cuando haya nuevas features relevantes.
- `network_mode: host` expone todos los puertos del host al contenedor. Es aceptable para ialab (nodo privado, sin exposición a internet). Si en F4+ hay workers que exponen puertos propios, evaluar red bridge explícita.
- La imagen incluye tanto `worker_base/` como `worker_echo/` en el mismo contexto. Para workers de F4+ (whisper, llm, tts), se crearán imágenes separadas usando el mismo Dockerfile base — el patrón está establecido.
