# Fase 5 — Retrospectiva: Dashboard mínimo

**Fecha:** 2026-06-16
**Estimación:** ~27 h · **Real:** implementación en 1 día + verificación en navegador real el 2026-06-16 — **5/5 escenarios PASS**

> Nota de alcance: la corrida e2e se ejecutó el 2026-06-16 (`docs/RUNBOOKS/e2e-f5-results.md`). La verificación inicial fue sin navegador (contrato API con curl). Un segundo pase con Chromium headless (Playwright) cerró el criterio visual. Un defecto de CORS se encontró y resolvió durante esa pasada — exactamente el gap que el runbook había marcado como pendiente.

---

## 1. ¿Qué tomó más tiempo del esperado?

**El bug de CORS, que solo aparece en navegador.** La primera corrida de verificación se hizo con `curl`, que verifica el contrato HTTP pero no dispara el preflight `OPTIONS` — ese mecanismo es exclusivo de navegadores. El runbook marcó los criterios "desde la UI" como no verificados por falta de navegador en sesión. Cuando se probó en un navegador real, el dashboard cargaba pero todas las llamadas a `/admin/jobs` y `/admin/workers` fallaban con `No 'Access-Control-Allow-Origin' header is present on the requested resource`. El fix fue agregar un middleware `withAdminCORS` en `api/main.go` que envuelve **todo el mux**, no los handlers individuales.

El motivo por el que el middleware tiene que envolver el mux (y no estar dentro de cada handler) es un comportamiento de Go 1.22+: `http.ServeMux` responde automáticamente `405 Method Not Allowed` a `OPTIONS` sobre rutas registradas solo con `GET`/`POST` **antes de que corra ningún handler**. Si el CORS va dentro del handler, el preflight ya fue rechazado por el mux con 405. Diagnosticar esta interacción requirió leer el comportamiento de Go 1.22 en detalle — no es obvio.

**`VITE_API_URL` no estaba en el `.env` real del VPS.** El `deploy.sh` ya la requería (se añadió a `REQUIRED_VARS` en T5.7), pero el `.env` real en el VPS no la tenía desde el comienzo de F5 — solo estaba en `.env.example`. Al intentar el primer deploy de F5, el script abortó con "missing required vars". Hubo que añadirla manualmente al VPS antes de poder desplegar. Es el mismo patrón de F4 ("variable en `.env.example` pero no en el `.env` real"), que se pensaba haber cerrado con la validación del `deploy.sh`.

---

## 2. ¿Qué fue más difícil?

**Entender que la verificación con `curl` es insuficiente para APIs consumidas por navegador.** Los cuatro criterios de aceptación de T5.8 que dicen "desde la UI" o "en la UI" tienen un subtexto que `curl` no puede verificar: que el navegador pueda hacer el request sin que el CORS lo bloquee. `curl` no envía `Origin`, no hace preflight, no lee `Access-Control-Allow-Origin`. Un endpoint que pasa 100% de los tests de integración y 100% de los curls puede fallar completamente en un navegador. Esta brecha entre "contrato API verificado" y "funciona en navegador" es real y requiere una pasada de verificación diferente.

**La variable de Vite es de build-time, no de runtime.** Cuando se despliega un container con `docker compose up --build`, `VITE_API_URL` se hornea en el bundle de JavaScript durante el `npm run build`. Si la variable cambia, hay que reconstruir la imagen — no alcanza con reiniciar el container. Esto contrasta con las variables de Go (que se leen en runtime del proceso) y generó confusión al razonar sobre "qué pasa si cambio `VITE_API_URL` en el `.env`". La respuesta es: nada, hasta el próximo `--build`.

## 3. ¿Qué automatizaría antes de F6?

**a) Test de preflight CORS como parte del healthcheck del deploy.** El `deploy.sh` ya verifica que el dashboard sirve (`curl -sf http://100.106.192.45:3000`). Debería también verificar que la API responde correctamente al preflight que el navegador va a hacer:

```bash
curl -sf -X OPTIONS http://100.106.192.45:8081/admin/jobs \
  -H "Origin: http://100.106.192.45:3000" \
  -H "Access-Control-Request-Method: GET" \
  -H "Access-Control-Request-Headers: X-Admin-Key" \
  -o /dev/null -w "%{http_code}" | grep -q 204
```

Si este check falla, el dashboard va a desplegar correctamente pero va a fallar en el navegador. El deploy debería detectarlo.

**b) Test de integración de CORS para rutas que el navegador va a consumir.** Ya existe `TestAdmin_CORS_PreflightAndHeaders` (añadido al resolver el bug), pero el principio debería generalizarse: cualquier endpoint que la UI va a consumir tiene que tener un test que verifique el preflight `OPTIONS` y los headers de respuesta. No es suficiente con probar el request real.

**c) Agregar `VITE_API_URL` al `.env` del VPS desde el script de bootstrap.** Hoy el `deploy.sh` la requiere pero no tiene un valor por defecto documentado más que el `.env.example`. Si el VPS se provisiona de nuevo, alguien tiene que acordarse de poner esa variable. Debería estar en la documentación de provisioning junto con `ADMIN_KEY` y `DATABASE_URL`.

## 4. ¿Qué documentación faltó?

**El comportamiento de Go 1.22+ con `OPTIONS` en `http.ServeMux`.** No está en ningún runbook ni en `DESIGN.md`. El patrón de "middleware de CORS debe envolver el mux completo, no los handlers" es específico de la versión de Go 1.22+ y contraintuitivo para quien viene de frameworks web que intercalan middleware por ruta. La decisión quedó documentada en el changelog de F5 (`docs/CHANGELOG/f5.md`, sección "T5.8 — Fix: CORS"), pero debería ser visible en `docs/` como patrón de la plataforma para cuando F9/F11 agreguen más endpoints con contexto de navegador.

**Que `VITE_API_URL` requiere rebuild para cambiar.** El `.env.example` la documenta como variable pero no dice que es de build-time. Un operador que quiera apuntar el dashboard a otra URL de API va a cambiarla en el `.env`, hacer `docker compose up -d` (sin `--build`), y quedar confundido de por qué no cambia nada. La nota está en el changelog y en `VPS.md` (añadida en T5.9), pero debería estar también en el `.env.example` como comentario.

**La brecha "curl ok / navegador falla" como patrón de verificación.** El runbook de F5 termina con la lección explícita, pero no está codificada en ningún template de checklist. Cualquier verificación de un endpoint que consume un navegador debería incluir al menos un preflight `OPTIONS` con `Origin` — no solo el request real.

## 5. ¿Qué aprendí sobre el sistema real?

**El tiempo de detección de worker offline es 93–129s, no <90s.** El criterio del plan (<90s) asumía que el monitor de heartbeat marca offline justo cuando el timeout expira. En realidad, el monitor corre en ticks de ~30s y solo procesa los workers que ya superaron el timeout en ese tick — lo que añade hasta 30s de latencia. El resultado (93–129s) es consistente y predecible, no un bug. El criterio era impreciso, no la implementación. Se ajustó a ≤120s en `IMPLEMENTATION_PLAN.md`.

**El admin key en `sessionStorage` fue la elección correcta.** `sessionStorage` limita el scope a la pestaña actual y se limpia al cerrar. `localStorage` persiste entre sesiones (conveniente pero riesgo si el equipo queda desbloqueado). Cookie httpOnly habría sido más seguro pero requería un endpoint de login y lógica de sesión del lado del servidor — scope creep. La elección eliminó además la preocupación de CSRF con `Access-Control-Allow-Origin: *`: sin cookies no hay credenciales implícitas del navegador, así que el wildcard es seguro.

**`curl` y el navegador son clientes fundamentalmente distintos para la misma API.** Más allá del CORS: el navegador envía `Origin`, hace preflights, rechaza requests cross-origin sin headers explícitos, y respeta políticas de CORS que `curl` ignora completamente. Verificar un endpoint con `curl` y declararlo "listo para el navegador" es una suposición incorrecta que esta fase materializó como bug.

**El polling de 5s es invisible para el operador y suficiente para la operación.** En ningún momento de la verificación se sintió que los datos estaban "viejos". El criterio del plan ("actualización automática sin acción del usuario") se cumple de forma completamente transparente — el operador no sabe que hay un setInterval corriendo cada 5s porque el dashboard sencillamente está actualizado cuando lo mira.

## 6. ¿Qué me sorprendió?

**El CORS fue completamente invisible hasta que alguien abrió un navegador.** Diez tests de integración, múltiples corridas con `curl`, el contrato API 100% verificado — y el dashboard no funcionaba en producción. El bug existía desde que se escribió el primer handler de `/admin/*` (T5.1) y ningún mecanismo de verificación lo detectó hasta la pasada con navegador real. Es el tipo de defecto que vive en la capa entre el protocolo HTTP (donde `curl` lo ve perfectamente) y el modelo de seguridad del navegador (donde CORS entra en juego).

**La pila completa del dashboard (T5.4–T5.6) fue más rápida de implementar que los endpoints de la API (T5.1–T5.3).** El React con polling, la autenticación por sessionStorage y el panel de workers/jobs tomaron menos tiempo que las queries SQL y los handlers de Go. La complejidad real de F5 estuvo en el deploy (T5.7) y en la verificación (T5.8), no en el código de la UI.

**La condición de carrera del setup de prueba reveló que el sistema funciona demasiado bien.** Al intentar cancelar un job `pending` desde el navegador, el worker lo reclamó antes de que se pudiera hacer clic — el job pasó de `pending` a `running` a `error` (SSRF) en segundos. Hubo que detener el worker para crear un job que permaneciera `pending` el tiempo suficiente para hacer clic. Esto es exactamente el comportamiento esperado del sistema (claim rápido por long-polling), pero resultó ser un obstáculo para el test manual del botón de cancelar.

## Decisiones que funcionaron bien

- **`withAdminCORS` envolviendo el mux completo:** la alternativa (un middleware por ruta o dentro de cada handler) habría fallado igualmente por el comportamiento de Go 1.22+ con `OPTIONS`, y requería más código repetido. Un solo punto de intercepción antes del routing es la solución correcta y mínima.
- **No implementar SSE en F5:** el polling de 5s satisface todos los criterios de aceptación con cero complejidad adicional en la API. SSE requería manejo de conexiones persistentes, reconexiones, y cambios en la arquitectura de la API. La presión de "el tiempo real sería mejor" no era suficiente para justificar el scope — y la fase lo dice explícitamente: "SSE → F11".
- **La verificación en navegador real como paso separado, no asumida:** el runbook marcó los criterios "desde la UI" como `⬜ NO VERIFICADO` hasta que hubiera un navegador disponible. Esta honestidad sobre lo que no se había verificado fue lo que permitió detectar el CORS en lugar de cerrarlo como "verificado" por proxy.
- **Reusar jobs reales del corpus SSRF de F4.5 para el e2e:** el job `377e0e29` (con `audio_url` http://, `retry_count=3/3`, `error_msg` de SSRF) era exactamente el caso de prueba ideal para verificar retry — un job que había fallado por razones conocidas, en estado terminal, con todos los campos de diagnóstico poblados. No fue necesario crear fixtures especiales.
