# Fase 2 — Retrospectiva: Node Agent

**Fecha:** 2026-06-13  
**Estimación:** ~32 h · **Real:** ~32 h código + ~3 h deploy/verificación en hardware

---

## 1. ¿Qué tomó más tiempo?

El bootstrap del entorno real tomó desproporcionadamente más tiempo que cualquier tarea de código. La implementación (T2.1–T2.11) se completó en dos días, pero el día de verificación (T2.12) tomó ~3 horas que no estaban presupuestadas — y todo fue deploy:

- El VPS tenía un stub de busybox en lugar de la API real. Nunca se había hecho un deploy de la imagen Go.
- El `.env` del VPS no tenía `ADMIN_API_KEY`.
- La API estaba ligada a `127.0.0.1:8081`, no accesible desde ialab vía Tailscale.
- No había procedimiento documentado para registrar un worker ni para generar su API key.

Dentro del código, **T2.7 (loop + buffer + backoff)** fue la tarea que requirió más diseño: decidir el tamaño del buffer, la estrategia de backoff, cómo hacer el loop testeable sin GPU ni red, y cómo manejar el lote de reconexión preservando los timestamps.

---

## 2. ¿Qué fue más difícil?

**El binding de red** fue lo más no-obvio. El agente recibía "Connection refused" al conectarse al VPS, y el proceso en el VPS estaba corriendo y escuchando — pero en `127.0.0.1:8081`. Desde el propio VPS funcionaba; desde ialab vía Tailscale, nada. El síntoma no distingue entre "el proceso no existe" y "escucha en la interfaz equivocada".

**La secuencia de bootstrap del agente** también fue difícil de primera vez: el agente necesita un `AGENT_API_KEY` para reportar métricas, pero esa key solo existe después de registrar el worker con el `ADMIN_API_KEY`. El `agent.env.example` dice `change_me_worker_api_key` sin explicar de dónde viene ese valor ni cómo generarlo.

En el código, lo más difícil fue diseñar `Reporter` de forma que el loop fuera testeable sin infraestructura real. La solución — inyectar `collect_fn` como parámetro — resultó limpia, pero no fue obvia desde el principio.

---

## 3. ¿Qué automatizaría antes de F3?

**a) Script de deploy del VPS.** No existe. El proceso manual es `git pull → docker compose down → docker compose up --build → migrate up`. Antes de F3 (que va a modificar la API) debería haber un `deploy/vps/deploy.sh` que haga exactamente eso, con validación de que el `.env` está completo antes de levantar.

**b) Bootstrap del agente en `install-agent.sh`.** El script ya instala el agente, pero si el `agent.env` no está rellenado, el servicio arranca y muere en loop. El script debería detectar que la worker key no está configurada, registrar el worker automáticamente usando el `ADMIN_KEY`, y completar el `.env` con la key generada. El bootstrap pasaría de 4 pasos manuales a 1.

**c) Healthcheck post-instalación.** Después de `systemctl restart node-agent`, no hay verificación de que el agente efectivamente está reportando. Una comprobación simple al final del script de instalación — esperar 20s y verificar que `worker_metrics` tiene filas recientes — convertiría el "parece que funciona" en un "confirmado".

---

## 4. ¿Qué documentación faltó?

**Procedimiento de deploy del VPS.** `docs/VPS.md` tiene la info de infraestructura pero no "cómo actualizar la API cuando hay código nuevo". Alguien que vuelva al proyecto en 3 meses no sabría que hay que hacer `--build`, que el `.env` va en `deploy/vps/`, ni que las migraciones corren por separado.

**Primera instalación del agente desde cero.** `docs/IALAB.md` documenta bien cómo operar el agente ya instalado. No documenta la secuencia de primera vez: generar la worker key, registrar el worker en la API, completar el `.env`. El lector tiene que inferir esto del template.

**Convención de puertos Tailscale.** No existe ningún documento que diga "los servicios que necesitan ser alcanzables entre nodos deben ligarse a la IP Tailscale, no a `127.0.0.1`". Esto se descubrió en producción. Debería estar en `docs/PORTS.md` como regla explícita.

---

## 5. ¿Qué aprendí del IA Lab real?

**La VRAM nunca está completamente libre.** El ledger calcula `vram_total_mb - vram_reserved_mb = 16376 MB libres` cuando no hay jobs. La GPU real reporta ~14.6 GB libres. Los ~1.7 GB los consume el SO, los drivers de NVIDIA y procesos del sistema que siempre están corriendo. Esto no es un bug — es una constante del hardware. El margen de 512 MB del drift alert siempre va a dispararse porque la deriva real es ~1.7 GB.

**Consecuencia directa para F3:** el scheduler no debería usar `vram_total_mb` como techo disponible. Debería usar `vram_free_mb` reportado por el agente, que refleja la realidad. Eso es exactamente para lo que T2.10 (alerta de deriva) fue diseñado como insumo diagnóstico.

**El backoff funcionó exactamente como se diseñó.** Durante el outage de 7 minutos, los logs mostraron la secuencia 5s → 10s → 20s → 40s → 80s → 160s → 300s. Al reconectar, el lote llegó con los `recorded_at` de captura reales — el gap quedó visible en la BD exactamente como los tests de integración lo verificaban. Los tests cubrían el contrato correcto.

**Tailscale es infraestructura confiable.** En ningún momento durante las pruebas — reboot de ialab, outage del VPS, kill -9 al agente — hubo problemas de conectividad Tailscale. La red privada entre nodos se mantuvo estable durante toda la sesión.

---

## Decisiones que funcionaron bien

- **`deque(maxlen=360)` para el buffer:** drop-oldest automático sin código extra. Se llenó durante el outage largo y funcionó.
- **`collect_fn` inyectable:** permitió testear el loop completo sin GPU ni servidor. Los 21 tests del reporter cubrían el comportamiento que luego se verificó en el outage real.
- **No auto-corregir el ledger (T2.10):** la deriva de ~1.7 GB que se vio en producción habría causado correcciones continuas con ruido del SO. Solo logging fue la decisión correcta.
- **Testcontainers en los tests de Go:** `TestMetricsBufferFlushPreservesTimestamps` verificó en PostgreSQL real que los `recorded_at` de un lote se preservan. El hardware lo confirmó. Segunda fase donde los tests contra BD real detectan comportamiento que mocks no podrían.

---

## Riesgos que pasan a F3

| Riesgo | Impacto | Acción |
|---|---|---|
| Claim usa `vram_total_mb` como techo | Jobs de 15 GB fallan aunque no haya nada corriendo | Usar `vram_free_mb` del agente como input al claim |
| Deploy del VPS sin script | El próximo deploy (F3 modifica la API) será manual otra vez | Crear `deploy/vps/deploy.sh` antes del primer cambio de F3 |
| Bootstrap del agente no documentado | Si ialab se reinstala, el onboarding tarda horas | Documentar "primera instalación" en `docs/IALAB.md` |
| `Claim` en `workers/store.go` sin extraer | F3 agrega `max_concurrency` — la función crece más | Evaluar extracción a `internal/scheduler/` cuando F3 toque `Claim` (mismo criterio de retro F1) |
