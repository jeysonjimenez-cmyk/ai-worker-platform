# Fase 1 — Retrospectiva arquitectónica

**Fecha:** 2026-06-10

---

## 1. La función `Claim` es el scheduler, no un store

### Problema detectado

`workers/store.go::Claim` (~60 líneas) hace cinco cosas distintas en una transacción:
1. Carga las capabilities del worker desde la BD
2. Parsea el JSON de capabilities para filtrar servicios
3. Selecciona el job de mayor prioridad con SKIP LOCKED
4. Parsea el JSON de requirements del job para calcular VRAM
5. Reserva VRAM atómicamente en `gpus`
6. Transiciona el job a `running`
7. Actualiza `current_job_id` en el worker

Esto no es persistencia de workers ni de jobs. Es el algoritmo de asignación de la plataforma. Vive en `workers/store.go` por accidente —  fue el primer lugar donde se necesitó, no porque pertenezca ahí.

### Riesgo concreto para F2

F2 agrega el Node Agent con métricas reales de GPU (`worker_metrics.vram_free_mb`). Cuando se integre ese filtro en el claim, la función toca cuatro tablas (`workers`, `jobs`, `gpus`, `worker_metrics`) dentro de una sola transacción. F3 agrega `max_concurrency > 1` para algunos workers (TTS: 2, embeddings: 4), lo que requiere contar jobs en ejecución por worker antes de asignar. Ambos cambios van en la misma función. Sin separación, cada nueva regla de asignación crece dentro de `Claim` sin un lugar claro donde vivir.

### Acción recomendada

No actuar ahora. Cuando F2 toque `Claim` por primera vez para agregar el filtro de `vram_free_mb`, ese es el momento de extraerlo a `internal/scheduler/claim.go`. La señal concreta es: si la función supera 80 líneas o toca más de 3 tablas, se ganó una capa.

**Prioridad:** Media — no duele hoy, duele en F2/F3.

## 2. `serviceRequirements` vive en el handler

### Problema detectado

```go
// jobs/handler.go:14
var serviceRequirements = map[string]int{
    "transcription":   10000,
    "video_generation": 14000,
    ...
}
```

Este mapa es conocimiento de dominio: cuánta VRAM necesita cada servicio por defecto. Vive en la capa HTTP (`handler.go`). Si el claim necesita este conocimiento en algún momento (para pre-filtrar en el query), habría que importar `jobs/handler.go` desde `workers/store.go`, o duplicarlo.

### Riesgo concreto para F2

Bajo en F2. El claim actualmente no usa este mapa — solo aplica lo que ya está guardado en `jobs.requirements`. El riesgo real llega cuando se agreguen servicios nuevos: el desarrollador busca en `workers/store.go` (que es donde está la lógica de asignación) y no encuentra la tabla de defaults. Los defaults están en el handler, no donde alguien esperaría.

### Acción recomendada

Moverlo a `jobs/service.go` o al mismo `jobs/retry.go` como segundo archivo de política. No urgente, pero es un cambio de dos líneas que clarifica dónde vive el conocimiento de dominio.

**Prioridad:** Baja.

## 3. `Cancel` hace un GET extra para disparar el webhook

### Problema detectado

```go
// jobs/handler.go:264
job, _ := Get(r.Context(), h.pool, jobID)
if job != nil && job.WebhookURL != nil {
    h.dispatcher.Dispatch(...)
}
```

La función `Cancel` en el store devuelve solo el status final (`string`), no el job completo. Entonces el handler hace un segundo round-trip a la BD para obtener el `webhook_url`. Este patrón ya existe en `Complete` también — pero `Complete` sí devuelve el job completo desde el `RETURNING`.

La inconsistencia es que `Cancel` y `Complete` hacen lo mismo (transición terminal + webhook) pero el store los trata diferente: uno devuelve el job, el otro no.

### Riesgo concreto para F2

Ninguno inmediato. Pero cuando F2 agregue más caminos terminales (ej. timeout automático que también dispara webhook), el patrón fragmentado hace que cada nuevo camino tenga que recordar si el store devuelve suficiente info o si necesita el GET extra.

### Acción recomendada

Hacer que `Cancel` devuelva `(*Job, error)` con el mismo patrón que `Complete`. Elimina el GET extra y hace el contrato consistente.

**Prioridad:** Baja — es un refactor de 10 líneas, sin urgencia real.

## 4. `ClaimResult` es código muerto

### Problema detectado

```go
// workers/store.go:108
type ClaimResult struct {
    Job *jobs.Job
}
```

Este tipo está declarado pero nunca se usa. `Claim` devuelve `*jobs.Job` directamente. `ClaimResult` es un wrapper que quedó de una intención anterior.

### Riesgo concreto para F2

Ninguno en términos de corrección. Confusión para quien lee el código por primera vez.

### Acción recomendada

Borrar las tres líneas.

**Prioridad:** Baja — limpieza puntual.

## 5. `gpu_id` hardcodeado como `hostname + "/gpu-0"`

### Problema detectado

```go
// workers/store.go:53
id := p.Hostname + "/gpu-0"
```

El registro de workers asume que cada host tiene exactamente una GPU y la nombra `gpu-0`. Esto es correcto para ialab hoy (solo RTX 4070 Ti Super). El DESIGN.md menciona que llegará una AMD Radeon AI PRO R9700.

### Riesgo concreto para F2

Ninguno en F2. El riesgo aparece en F8+ cuando ialab tenga dos GPUs. Si en ese momento la convención ya está usada en decenas de registros en la BD de producción, cambiar el esquema tiene costo de migración.

### Acción recomendada

En el payload de registro, el worker debería declarar su `gpu_id` explícitamente en lugar de que el servidor lo derive. Cambio en `RegisterParams` y en el worker simulado. Hacerlo antes de que haya datos reales en producción (antes de F4 cuando arrive el primer worker real).

**Prioridad:** Media — no urgente para F2, pero se ganó hacerlo antes del primer deploy real.

## 6. `vram_released` como campo en `jobs`

### Problema detectado

El flag `vram_released BOOLEAN` se agregó a la tabla `jobs` durante la implementación para resolver idempotencia en `ReleaseVRAMReservation`. Es funcional y correcto.

El detalle: este campo no es un atributo del job sino un detalle de implementación del ledger de VRAM. Un job `done` con `vram_released = false` no tiene sentido desde el punto de vista del dominio — significa que el ledger quedó inconsistente.

### Riesgo concreto para F2

Bajo. El flag funciona. Pero en el dashboard (F5), si alguien consulta jobs y ve `vram_released: false` en un job `done`, genera confusión. También: la API de `GET /ai/jobs/{id}` expone este campo en la respuesta JSON porque el struct `Job` lo serialize todo — actualmente no está en el struct, pero si se agrega para debugging, queda expuesto al cliente.

### Acción recomendada

No cambiar nada ahora. Si en F5 el dashboard hace evidente que este campo confunde, ese es el momento de moverlo a una tabla auxiliar `job_vram_ledger` o de ocultarlo del response struct.

**Prioridad:** Baja — observar en F5.

## Decisiones que funcionaron bien

- **`retry.go`** separado: la extracción de `shouldRetry` y `nextRetryDelay` fue el único refactor que ocurrió durante F1 y resultó correcto — las dos funciones son policy pura, fácilmente localizables.

- **`ReleaseVRAMReservation` centralizada**: los cuatro caminos de liberación (complete, error, cancel, heartbeat timeout) convergen en una sola función. El test de doble liberación pasó limpio. Esta decisión del BACKLOG se respetó y valió la pena.

- **Testcontainers sobre mocks**: los tests de SKIP LOCKED y reserva atómica son los únicos que pueden detectar race conditions reales. El test de carrera del ledger (`TestVRAMLedgerRace`) verificó que 10 workers concurrentes no sobre-reservan. Con mocks de BD esto sería imposible de probar.

- **Long-polling en conexión dedicada**: usar `pool.Acquire()` para LISTEN en lugar de bloquear una conexión del pool fue la decisión correcta — evita starvar el pool cuando hay muchos workers esperando.
