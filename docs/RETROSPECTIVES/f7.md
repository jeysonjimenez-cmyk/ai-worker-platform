# Retrospectiva — Fase 7: worker-tts + migración completa 🏁

> F7 cerrada 2026-06-21. MVP completo: Video Crack opera sus tres servicios (transcripción, traducción, TTS) sobre la plataforma. Sistema viejo apagado.

---

## 1. ¿Qué tomó más tiempo del esperado?

**El motor TTS (T7.2 / T7.4).** El timebox de 2 días fue ajustado pero la integración de Higgs reveló una propiedad no documentada: SGLang-Omni no expone endpoint de flush (`/flush_cache` → 404). La única forma de liberar su VRAM es `docker stop`. Esto obligó a rediseñar el idle-unload: en vez del patrón "esperar idle timeout → llamar API del motor", se adoptó "unload inmediato tras cada job via Docker socket montado en el container". El cambio fue pequeño pero requirió descubrirlo empíricamente durante T7.11.

**La corrida de producción en `platform` mode (T7.12–T7.13).** Los bugs latentes en video-crack (parseo del resultado de traducción, SSRF sobre loopback, TTS auto-chain) solo se manifestaron al conmutar a `platform` — en `both` mode el sistema viejo enmascaraba todos esos defectos. El switch reveló tres bugs que en `both` eran invisibles.

---

## 2. ¿Qué fue más difícil?

**La calibración de VRAM de TTS.** El valor teórico (`2000`) estaba 12720 MiB por debajo del real (`14720`). Sin la medición de T7.2/T7.6, el ledger habría aprobado tres modelos simultáneos en una GPU que físicamente no los cabe. La exclusión mutua (TTS bloquea whisper/ollama y viceversa) emergió de la calibración, no del diseño original.

**Distinguir bugs de video-crack de bugs de la plataforma.** Los tres defectos encontrados al hacer el switch eran bugs de video-crack (no de la plataforma), pero los síntomas apuntaban al sistema en general: "el job de traducción falla", "connection refused", "la GPU no se mueve". Cada uno requirió leer los logs correctos (container vs. backend vs. plataforma) para aislar el origen.

---

## 3. ¿Qué automatizaría antes de la fase siguiente?

**El arranque del backend de video-crack con el env correcto.** Durante T7.13 el backend se reinició varias veces manualmente con `env $(cat .env.platform | xargs) uvicorn ...`. Un script de arranque o un servicio systemd que tome `.env.platform` evita que la sesión se pierda o que el backend vuelva a arrancar con un env incorrecto (el proceso viejo tenía `TRANSCRIBE_MODE=both` mientras el archivo ya decía `platform`).

**La verificación de env vars en el proceso vivo.** El patrón `cat /proc/$PID/environ | tr '\0' '\n' | grep MODE` se repitió múltiples veces. Un `make check-vc-env` o similar que compare el env del proceso con el `.env.platform` ahorraría tiempo diagnóstico.

---

## 4. ¿Qué documentación faltó?

**El comportamiento de SGLang-Omni respecto a flush/unload.** La decisión de usar `docker stop` en vez de una API del motor quedó documentada en el runbook y el changelog, pero no en DESIGN.md. Un lector nuevo que vea `docker.sock` montado en `worker-tts` no entendería por qué sin leer el changelog de T7.4/T7.11.

**El bug de parseo de resultado de traducción.** `result.get("result")` devuelve un dict (el resultado del worker) cuando se espera un string. Este comportamiento del SDK / API nunca estuvo documentado: el contrato de `client.wait()` dice "retorna el job object" pero no explicita la estructura de `result`. Un contrato escrito del formato de retorno habría evitado el bug en video-crack.

**Que `ALLOW_HTTP_AUDIO=1` es necesario cuando video-crack y el worker comparten el mismo nodo.** El caso de uso "cliente en loopback + worker en Docker host network" no estaba documentado en ningún runbook como configuración válida.

---

## 5. ¿Qué aprendí sobre Tailscale, Docker o la operación real?

**`network_mode: host` no equivale a acceder loopback del host desde fuera.** El worker-whisper corre con `network_mode: host` y por eso sí puede llegar a `127.0.0.1:8000`. Pero la SSRF policy bloqueaba `http://` (solo permite `https`) y también `100.64.0.0/10` (bloque Tailscale). `ALLOW_HTTP_AUDIO=1` saltea ambas validaciones — lo correcto para un deployment donde cliente y worker comparten máquina.

**Docker socket montado en un container es la única salida cuando el servicio no expone API de shutdown.** SGLang-Omni (Higgs) no tiene endpoint de flush. Montar `/var/run/docker.sock` en `worker-tts` y llamar `docker stop ialab-higgs-tts-1` es la solución idiomática — pero implica dar al container privilegios de Docker, lo que debe ser una decisión consciente de seguridad.

**`docker compose up -d --force-recreate` vs. `restart`:** ya lo sabíamos de retros anteriores, pero F7 lo confirmó una vez más: el proceso viejo de uvicorn (PID 190708) tenía el env del arranque anterior (`TRANSCRIBE_MODE=both`) aunque el archivo `.env.platform` dijera `platform`. Matar y rearrancar el proceso es el único way de que tome el nuevo env.

---

## 6. ¿Qué me sorprendió del comportamiento del sistema distribuido?

**Los bugs de `both` mode se vuelven bugs bloqueantes en `platform` mode.** En `both`, la ruta legacy siempre produce un resultado primario válido; la ruta platform corre en background y sus fallos son eventos secundarios. Al conmutar a `platform`, exactamente los mismos fallos se vuelven bloqueantes: el parseo roto de la respuesta de traducción, la SSRF sobre loopback, el TTS auto-chain no deseado. El "modo de validación" oculta sistemáticamente los bugs de integración hasta el switch.

**La exclusión mutua emergió de la física, no del diseño.** TTS (14720 MiB) + whisper (5500 MiB) = 20220 > 15946 MiB → el ledger bloquea la coexistencia sin necesidad de lógica especial. El diseño original esperaba "tres modelos a la vez"; la realidad es que el ledger implementa exclusión mutua automáticamente cuando los picos reales superan la mitad de la VRAM total. Esto es una propiedad emergente correcta — pero hay que medir para descubrirla.

**El job de traducción japonés reveló un bug latente en el parseo.** El worker-ollama siempre devolvió `{"result": "1. texto\n..."}` y `result.get("result")` siempre devolvió un dict. En los jobs anteriores que "funcionaban" (en `both` mode), el resultado de la plataforma nunca se usaba para construir los subtítulos primarios — iba al archivo `.platform.vtt` de comparación, y ese path también tenía el mismo bug pero nadie lo notó porque el archivo simplemente quedaba vacío. El switch a `platform` mode fue el primer momento en que el parseo fallido se convirtió en un error visible.

## Deuda técnica identificada (para post-MVP)

- Script de arranque de video-crack backend con `.env.platform` (systemd o similar)
- Documentar en DESIGN.md la decisión de `docker.sock` para workers cuyo motor no expone API de shutdown
- Contrato escrito del formato de `result` en `client.wait()` (actualmente implícito)
- `concurrency: 2` para TTS diferido — throughput de TTS podría ser cuello si se procesan muchos videos simultáneos
