## Ver jobs por estado

```sql
-- Todos los jobs recientes, agrupados por estado
SELECT status,
       COUNT(*)                              AS total,
       MAX(created_at)                       AS ultimo_creado
FROM jobs
GROUP BY status
ORDER BY total DESC;

-- Últimos 20 jobs (más reciente primero)
SELECT id,
       app,
       service,
       status,
       progress,
       retry_count,
       to_char(created_at AT TIME ZONE 'UTC', 'HH24:MI DD-Mon') AS creado,
       to_char(completed_at AT TIME ZONE 'UTC', 'HH24:MI DD-Mon') AS completado
FROM jobs
ORDER BY created_at DESC
LIMIT 20;

-- Jobs por estado concreto: 'pending' | 'running' | 'done' | 'error' | 'cancelled'
SELECT id, app, service, status, progress, retry_count, created_at
FROM jobs
WHERE status = 'pending'
ORDER BY priority, created_at
LIMIT 20;
```

## Diagnosticar un job fallido

Caso de uso principal: doble ejecución — un job de plataforma en estado `error`.

```sql
-- Detalle completo: error, payload, worker asignado
SELECT j.id,
       j.status,
       j.error_msg,
       j.retry_count,
       j.max_retries,
       j.retry_after,
       j.worker_id,
       j.payload,
       j.result,
       j.created_at,
       j.started_at,
       j.completed_at
FROM jobs j
WHERE j.id = :'JID';

-- Logs del job (orden cronológico)
SELECT level,
       message,
       to_char(created_at AT TIME ZONE 'UTC', 'HH24:MI:SS') AS hora
FROM job_logs
WHERE job_id = :'JID'
ORDER BY created_at;

-- Archivos de salida registrados
SELECT filename, path, size_bytes, created_at
FROM job_files
WHERE job_id = :'JID';
```

-- Listar todos los jobs de un workflow

## Estado de workers

```sql
-- Estado actual de todos los workers
SELECT id,
       status,
       current_job_id,
       to_char(last_heartbeat AT TIME ZONE 'UTC', 'HH24:MI:SS DD-Mon') AS ultimo_heartbeat,
       capabilities->>'services' AS servicios
FROM workers
ORDER BY last_heartbeat DESC NULLS LAST;

-- VRAM actual del GPU de ialab
SELECT g.id,
       g.vram_total_mb,
       g.vram_reserved_mb,
       g.vram_total_mb - g.vram_reserved_mb AS vram_libre_mb
FROM gpus g
JOIN workers w ON w.gpu_id = g.id
WHERE w.status = 'idle' OR w.status = 'busy';
```

## Acciones de operación

### Cancelar un job `pending` (vía API — recomendado)

Requiere la `X-App-Key` de la app dueña del job.

```bash
APP_KEY="ak-<key-de-video-crack>"
API="http://100.106.192.45:8081"
JOB_ID="<job-id>"

curl -s -X POST "$API/ai/jobs/$JOB_ID/cancel" \
  -H "X-App-Key: $APP_KEY"
# → {"status":"cancelled"}
# → 409 si el job ya está en estado terminal
```

> El endpoint libera la VRAM si el job estaba `running` y dispara el webhook de `cancelled`.

### Cancelar un job `pending` (vía SQL — solo sin API key disponible)

```sql
-- Verificar estado antes
SELECT id, status, app FROM jobs WHERE id = :'JID';

-- Cancelar (solo si status = 'pending'; no libera VRAM porque no hay reserva en pending)
UPDATE jobs
SET status = 'cancelled', completed_at = now()
WHERE id = :'JID' AND status = 'pending';
-- RowsAffected = 0 → el job no era pending o no existe
```

> Usar el endpoint de API siempre que sea posible; el UPDATE directo no dispara webhooks.

### Re-encolar un job `error` que agotó reintentos

Los reintentos automáticos ocurren cuando `retry_count < max_retries` (default: 3 intentos con backoff 30s/60s/120s). Si el job está en `error` con `retry_count >= max_retries`, re-encolar manualmente:

```sql
-- Verificar que el job agotó reintentos
SELECT id, status, retry_count, max_retries, error_msg
FROM jobs
WHERE id = :'JID';
-- Proceder solo si status = 'error' y retry_count >= max_retries

-- Re-encolar: volver a pending con contador reseteado
UPDATE jobs
SET status       = 'pending',
    worker_id    = NULL,
    started_at   = NULL,
    completed_at = NULL,
    error_msg    = NULL,
    retry_count  = 0,
    retry_after  = NULL,
    vram_released = false
WHERE id = :'JID' AND status = 'error';
-- Confirmar: SELECT status FROM jobs WHERE id = :'JID';
```

> `vram_released = false` es necesario para que la próxima ejecución pueda reservar VRAM.
> Notificar a los workers del nuevo pending:
>
> ```sql
> SELECT pg_notify('jobs_channel', :'JID');
> ```

## Queries de monitoreo rápido (doble ejecución)

```sql
-- Jobs de Video Crack en las últimas 2 horas
SELECT id, status, error_msg, retry_count,
       to_char(created_at AT TIME ZONE 'UTC', 'HH24:MI:SS') AS creado
FROM jobs
WHERE app = 'video-crack'
  AND created_at > now() - interval '2 hours'
ORDER BY created_at DESC;

-- Jobs stuck en running (sin heartbeat del worker > 3 min)
SELECT j.id, j.service, j.progress, j.started_at, w.last_heartbeat
FROM jobs j
LEFT JOIN workers w ON w.id = j.worker_id
WHERE j.status = 'running'
  AND (w.last_heartbeat IS NULL OR w.last_heartbeat < now() - interval '3 minutes');
```
