El problema que resuelve: el worker descarga un audio_url que viene del payload de un cliente. Sin validación, un atacante podría apuntar a IPs internas del tailnet o a metadata endpoints (SSRF). Se replica la política del paquete ssrf de Go (F1), ahora en Python para el lado worker.

DNS resuelto antes de descargar (late-binding SSRF)

La validación resuelve el DNS antes de iniciar la descarga, no confía en el hostname. Sin esto, un dominio que resuelve a una IP pública en la validación y a una privada en la descarga (DNS rebinding) burlaría el control.

T4.5
Gestión de modelo: carga lazy + descarga por inactividad
El modelo se carga al primer job y se descarga tras 10 min de inactividad, llamando POST /workers/{id}/unload-model para liberar la reserva del ledger (endpoint de F1, reutilizado).
Desarrollo 3 h
✅ 2026-06-15
▼

El problema que resuelve: un modelo de ~5 GB en VRAM bloquea esa memoria para otros workers (relevante para la convivencia de F6). Si nadie usa whisper, su VRAM debe liberarse sin intervención y volver a cargarse sola al siguiente job.

Implementación
  • workers/worker_whisper/__init__.py— model manager: globals _model, _model_lock, _active_jobs, _last_released; _acquire_model() (carga lazy + contador), _release_model() (decrementa + resetea idle clock), _idle_watcher() (daemon thread cada 60s; descarga si _active_jobs == 0 y pasó ≥_IDLE_TIMEOUT). execute() en try/finally para garantizar _release_model()
  • workers/worker_base/api_client.py— unload_model(worker_id): POST /workers/{id}/unload-model con X-Worker-Key
  • workers/tests/test_whisper_execute.py— fixture autouse _reset_model_state + 10 tests nuevos: carga, reuso, contador, release en éxito/error, recarga tras unload, watcher con/sin job activo y antes/después del timeout
Configuración por env vars
VariableDefaultDescripción
WHISPER_IDLE_TIMEOUT600Segundos de inactividad antes de descargar el modelo
El lock se mantiene durante la llamada a unload-model (anti-TOCTOU)

Sin el lock, un nuevo job podría cargar el modelo entre el momento en que el watcher decide descargar y la notificación al ledger, dejando el ledger con VRAM = 0 mientras el modelo está realmente cargado. El lock cierra esa carrera.

T4.8
Timeout máximo por job, configurable por service
Timeout de ejecución por job, configurable por service (transcription: 4h, llm_chat: 30m...). Un job running que lo excede libera VRAM y reintenta/marca error. Distinto del heartbeat (90s).
Desarrollo · API Go 3 h
✅ 2026-06-15
▼

El problema que resuelve: un job atascado (modelo colgado, bug de inferencia) no debe consumir VRAM indefinidamente. Pero un audio de 1 h tarda minutos legítimos — el timeout debe ser por service, no global, para no matar jobs largos válidos.

Implementación
  • api/internal/jobs/handler.go— serviceMaxDuration (transcription: 4h, llm_chat: 30m…); exporta ServiceMaxDurations() para el monitor
  • api/internal/jobs/store.go— FailTimedOutJobs(): itera por service, FOR UPDATE SKIP LOCKED (seguro ante llamadas concurrentes), ReleaseVRAMReservation y reencola o marca error según retry_count < max_retries
  • api/internal/monitor/monitor.go— en tick() llama jobs.FailTimedOutJobs(...) tras el check de heartbeat; errores se loguean sin interrumpir el tick
Tests de integración
  • TestJobTimeout_ExhaustedRetries: max_retries=0 pasado 2h → error
  • TestJobTimeout_SchedulesRetry: max_retries=2 → pending + retry_after
  • TestJobTimeout_WithinLimit_NotAffected: 5 min, límite 30 min → sigue running
  • TestJobTimeout_ReleasesVRAM: vram_reserved_mb vuelve a 0 tras timeout
Tiempo absoluto, no intervalo PostgreSQL

El timeout usa started_at < $cutoff con el corte calculado en Go, no un intervalo SQL, para evitar dependencia del formato de time.Duration.String(). Es independiente del heartbeat (90s): acota la duración total, no la ausencia de señal.

El problema que resuelve: whisper es el primer worker que reserva VRAM real (10 GB teóricos). La retro de F3 advirtió que el valor era teórico y el overhead de SO ~1.7 GB superaba el margen de 500 MB. La medición real mostró pico de 4443–4667 MB — el valor teórico era 2× demasiado conservador.

MIN_VRAM_TRANSCRIPTION_MB100005500 (pico 4667 + 833 margen)

No reemplazar el ledger por vram_free_mb

El ledger previene la carrera de doble-claim; vram_free_mb solo sirve para detectar deriva (T2.10). El tradeoff de 5500 MB: demasiado justo y OOM mata el worker; demasiado amplio y bloquea otros jobs. 5500 = pico medido 4667 + 833 de margen — razonado, con incertidumbre sobre audios muy largos.

5 defectos de integración encontrados y corregidos
Build colgado por tzdata (DEBIAN_FRONTEND ausente)

El build de Dockerfile.whisper se colgó esperando input interactivo de tzdata ("Geographic area:"). Antipatrón de Docker+Ubuntu conocido desde los 2000, invisible hasta correr en una máquina limpia. Sin linter de Dockerfiles que lo atrapara.

make deploy solo sincroniza al VPS, no a ialab

El repo en ialab tenía código viejo (sin Dockerfile.whisper). Hay que rsync manual a ialab además del deploy — no documentado como paso obligatorio. Pasa como deuda a F4.5 (deploy-ialab target).

FILE_SERVER_URL en .env pero no en docker-compose.yml

La variable estaba en el .env del VPS pero el environment: del servicio api no la referenciaba — nunca llegaba al contenedor. La API arrancaba sin error (variable opcional) y el proxy devolvía 503 para todos los archivos. Bug silencioso y confuso.

Hosts públicos de audio caídos → escape hatch SSRF

transfer.sh y 0x0.st estaban caídos. El SSRF exige https:// y bloquea IPs Tailscale. Se agregó ALLOW_HTTP_AUDIO=true para servir desde ialab sin HTTPS — parche funcional para el e2e, no diseño final. Debe removerse del env de ialab tras el e2e.

Disco lleno en ialab (430G/430G)

El build de whisper falló por falta de espacio: 82 GB de imágenes Docker sin usar de otros proyectos. Docker arranca contenedores cacheados con 0 bytes libres, así que el problema es invisible hasta que intentas build o pull.

Retrospectiva — aprendizajes clave

Lo que funcionó bien

  • ALLOW_HTTP_AUDIO como escape hatch explícito: prod sin la var → SSRF activo; testing la activa
  • MIN_VRAM_TRANSCRIPTION_MB como env var: calibrar sin redeploy de código
  • Simular caos con docker compose stop: el heartbeat no distingue "contenedor parado" de "máquina apagada"
  • 5 defectos de setup, 0 de funcionalidad: todo el código de F4 corrió bien al primer intento

Lo que aprendimos del sistema real

  • 4.2 h de audio = ~28 min en RTX 4070 Ti SUPER (≈7 min por hora de audio)
  • VRAM estable 4443–4667 MB durante 4.2 h: sin leak en faster-whisper large-v2
  • El ledger de VRAM es sólido bajo carga real: reserva/libera sin intervención
  • Requeue por heartbeat real: 99s de timeout, pero job retomado en 3s tras start

Lo más difícil técnicamente

  • Calibrar VRAM: 10000 teórico vs 4667 real; fijar 5500 con margen razonado
  • El escape hatch SSRF: seguro en prod, difícil para testing local sin hosting público
  • Lock durante unload-model para cerrar la carrera TOCTOU del ledger
  • Progreso real por segmento sin saltar de 0 a 100 en jobs de media hora

Riesgos que pasan a F4.5

  • rsync manual a ialab no está en el flujo de deploy → deploy-ialab target
  • SSRF bloquea testing con URLs internas → ¿servir audios desde la URL pública del cliente?
  • VRAM pico puede subir con audiobuffers grandes → monitorear primeros jobs reales
  • ALLOW_HTTP_AUDIO=true debe removerse del env de ialab tras el e2e

Deuda técnica registrada para F4.5+

Sincronización a ialab fuera del flujo de deploy — make deploy solo sincroniza al VPS. ialab requiere rsync manual y no está documentado como paso obligatorio. Agregar target deploy-ialab al Makefile.
ALLOW_HTTP_AUDIO=true en el env de ialab — escape hatch del SSRF para el e2e. Si ialab pasa a producción, esa variable debe removerse del worker-whisper.env.
Margen VRAM de 5500 MB con incertidumbre — calibrado con audio estándar (pico 4667 + 833). Audio muy largo o con alta densidad de voz puede pedir más. Monitorear nvidia-smi en los primeros jobs de producción reales de Video Crack.
Env vars críticas sin healthcheck al arrancar — el patrón "variable en .env pero no pasada al contenedor" fue un bug silencioso (FILE_SERVER_URL). Un log "file_server_url=<valor> (vacío = proxy deshabilitado)" al iniciar la API evitaría esta clase de debug.
Verificación de disco en ialab antes del build — el build falló por disco lleno (430G/430G) sin diagnóstico previo. Una línea df -h en el target workers-build que falle si hay <5 GB libres.
Python 3.12 via deadsnakes en Dockerfile.whisper — add-apt-repository ppa:deadsnakes/ppa agrega latencia y dependencia de terceros. Alternativa más limpia: python:3.12-slim + CUDA libs aparte.
