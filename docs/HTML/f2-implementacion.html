El cliente declara su gpu_id en el payload de registro, en lugar de que el servidor lo derive como hostname+"/gpu-0".
Desarrollo Retro F1 #5

T2.3
Endpoint de ingesta de métricas en la API Go
POST /workers/{id}/metrics — recibe lotes de muestras del agente y las persiste en worker_metrics con el timestamp de captura del cliente.
Desarrollo 4 h
✅ 2026-06-10

El problema que resuelve: la API no tenía ninguna forma de recibir datos de telemetría del hardware. El agente necesitaba un endpoint autenticado que acepte lotes (para el buffer de reconexión) y que preserve el timestamp de captura del cliente, no el de llegada al servidor.

Qué se creó / cambió
  • api/internal/workers/store.go— Struct MetricSample con todos los campos (cpu_pct, vram_total/used/free, gpu_util, temperature, power, ram_used) y función IngestMetrics(ctx, pool, workerID, []MetricSample) que inserta en transacción.
  • api/internal/workers/handler.go— metricsRequest (array de samples) + handler IngestMetrics con validación de payload.
  • api/main.go— Nueva ruta POST /workers/{id}/metrics bajo el middleware de worker key.
Convenciones clave
recorded_at viene del cliente

El agente envía el timestamp exacto de cuando tomó la muestra. La API lo persiste tal cual, sin sobreescribirlo con now(). Esto es lo que hace posible que el buffer de reconexión funcione: al reconectar, el lote acumulado llega con los timestamps reales de captura.

Acepta lotes (array)

El endpoint recibe un array de muestras en lugar de una sola. Esto soporta directamente el caso de buffer: cuando el agente se reconecta, envía todas las muestras acumuladas en un solo POST.

Tests de integración (PostgreSQL real)
  • POST válido inserta todos los campos con el timestamp de captura
  • Lote de N muestras inserta N filas
  • Sin API key o con key de app → 401/403
  • Payload sin recorded_at → 422
  • Worker_id del path ≠ worker autenticado → 403
  • Campos GPU null en nodos sin GPU → aceptado

T2.5
Endpoint local /metrics del agente
Servidor HTTP mínimo que expone la última muestra en JSON. Bind explícito a la IP Tailscale, nunca a 0.0.0.0.
Desarrollo
✅ 2026-06-11

El problema que resuelve: los workers de F3 correrán en Docker en ialab. Desde un contenedor, 127.0.0.1 no es el host — no podrían consultar el estado del nodo. La solución es un servidor HTTP en la IP Tailscale del nodo, accesible desde cualquier contenedor y desde el VPS.

Qué se creó
  • agent/agent/metrics_server.py NEW— MetricsServer con update(sample) thread-safe (lock interno) y start(bind_addr) que lanza el servidor en un daemon thread. Responde 503 antes del primer sample, 404 en rutas desconocidas.
  • agent/agent/config.py— Añadido metrics_bind: str desde AGENT_METRICS_BIND. No tiene valor por defecto: si la variable no está configurada, el agente falla al arrancar con error claro. Nunca silencia a 0.0.0.0.
  • agent/tests/test_metrics_server.py NEW— 7 tests con servidor real en puertos efímeros (sin necesidad de root ni GPU).
Decisión de seguridad
AGENT_METRICS_BIND es obligatoria, sin default

El operador debe declarar explícitamente en qué dirección escucha el agente. Un default silencioso a 0.0.0.0 expondría el endpoint a cualquier interfaz de red, incluyendo las públicas. El valor operativo es siempre la IP Tailscale del nodo (100.103.55.110:9100).

Verificado en hardware real (2026-06-13)

  • curl http://100.103.55.110:9100/metrics desde el VPS vía Tailscale devuelve JSON correcto
  • No alcanzable desde internet público

T2.7
Loop de reporte cada 10s con buffer y reintentos
Loop principal que toma una muestra cada 10s. Si el VPS no responde, acumula en buffer y reenvía en lote al reconectar.
Desarrollo 4 h
✅ 2026-06-11

El problema que resuelve: si el VPS cae, el agente no debe crashear ni perder muestras. Al reconectar, el VPS debe recibir todas las muestras con sus timestamps de captura originales, no con el momento de llegada.

Qué se creó
  • agent/agent/reporter.py NEW— Reporter con buffer deque(maxlen=360) (drop-oldest automático = 1 hora a 10s/muestra). flush() envía el lote acumulado. Backoff exponencial: 5s → 10s → 20s → 40s → 80s → 160s → 300s (máximo). Se resetea a cero tras flush exitoso.
  • agent/agent/main.py NEW— Entry point: Config → registro → MetricsServer → Reporter → loop. No se testea directamente (es el pegamento de módulos ya testeados).
  • agent/tests/test_reporter.py NEW— 21 tests: buffer cap, flush success/failure, backoff, run_loop con collect_fn inyectado para testear sin GPU ni red.
Decisiones de diseño
deque(maxlen=N) para el buffer

Python's collections.deque con maxlen descarta las muestras más antiguas automáticamente cuando se llena. No requiere código extra de gestión de límite.

collect_fn inyectable en run_loop

El loop acepta una función de colección como parámetro. En producción es collect(); en tests es una función que devuelve datos simulados. Permite probar el comportamiento del loop (buffer, backoff, reintentos) sin GPU ni servidor real.

Verificado en hardware real (2026-06-13)
  • VPS caído 7 min → agente vivo, backoff hasta 300s, sin reinicios de systemd
  • Al reconectar: lote de ~42 muestras enviado, gap de 7 min visible en worker_metrics
  • recorded_at del lote = timestamps de captura reales, no momento de llegada
  • Cadencia volvió a 10s tras el lote

T2.10
Alerta de deriva ledger ↔ VRAM real
La API compara la VRAM libre reportada contra lo que el ledger predice. Si la diferencia supera 512 MB, emite un WARN en logs.
Desarrollo Observabilidad
✅ 2026-06-11

El problema que resuelve: el ledger de VRAM (vram_total - vram_reserved) puede desviarse de la realidad si hay bugs en la lógica de claim/release. Sin datos reales del hardware, estos bugs son invisibles. La alerta hace que cualquier deriva sostenida aparezca en logs desde el primer día con métricas reales.

Cómo funciona

Al ingerir métricas, la API toma el sample más reciente con vram_free_mb no nulo y lo compara contra gpus.vram_total_mb - gpus.vram_reserved_mb. Si la diferencia supera el margen configurado: WARN vram drift: gpu_id=... ledger_free_mb=... reported_free_mb=... delta_mb=...

Qué se cambió
  • api/internal/config/config.go— Campo VRAMDriftMarginMB desde VRAM_DRIFT_MARGIN_MB (default 512 MB).
  • api/internal/workers/store.go— Función pura vramDriftExceeded(ledger, reported, margin) + checkVRAMDrift best-effort (silencio en error o worker sin GPU). IngestMetrics recibe el margen y llama checkVRAMDrift tras el commit.
  • api/internal/workers/drift_test.go NEW— 8 casos unitarios para vramDriftExceeded: dentro del margen, en el límite exacto, un MB sobre el margen, delta inverso, margen cero.
Decisión consciente: solo log, sin corrección automática
Sin auto-corrección del ledger

El ledger es la fuente de verdad para el scheduler. Corregirlo automáticamente con métricas externas podría enmascarar bugs reales en la lógica de claim/release. La corrección automática se evalúa en F3+ cuando haya más datos de producción. En F2, el warning es insumo diagnóstico.

Verificado en hardware real (2026-06-13)
  • Ledger: 16376 MB libres (sin jobs en vuelo). GPU real: ~14.6 GB libres. Delta: ~1.7 GB por SO y drivers.
  • WARN aparece correctamente en logs de la API por superar el margen de 512 MB
T2.11
Job de retención de worker_metrics
Goroutine que cada 24h agrega las filas de más de 7 días a worker_metrics_hourly y borra las crudas.
Desarrollo 3 h
✅ 2026-06-11

El problema que resuelve: a 10s por muestra, worker_metrics crece ~8640 filas/día por worker. Sin retención, la tabla crece indefinidamente. El dashboard de F5 solo necesita detalle reciente; el histórico puede estar agregado por hora.

Schema de la tabla de agregados
CREATE TABLE worker_metrics_hourly (
  worker_id TEXT NOT NULL,
  hour TIMESTAMPTZ NOT NULL, -- truncado a la hora
  cpu_pct_avg NUMERIC, cpu_pct_max NUMERIC,
  vram_free_avg NUMERIC, -- promedio
  vram_free_min NUMERIC, -- peor caso de la hora
  gpu_util_avg NUMERIC, temperature_avg NUMERIC,
  power_avg NUMERIC, ram_used_avg NUMERIC,
  sample_count INTEGER,
  PRIMARY KEY (worker_id, hour)
);
Qué se creó
  • migrations/0003_worker_metrics_hourly.up.sql NEW— Tabla worker_metrics_hourly.
  • api/internal/retention/retention.go NEW— Compact(ctx, pool): INSERT … ON CONFLICT DO NOTHING + DELETE en la misma transacción. Run(ctx, pool) con tick de 24h.
  • api/main.go— go retention.Run(ctx, pool) junto a monitor.Run.
Clave de idempotencia
ON CONFLICT DO NOTHING + DELETE separado

Si el proceso se cae tras el INSERT pero antes del DELETE, la segunda ejecución encuentra el agregado ya existente (DO NOTHING) y completa el DELETE. El invariante es que si hay un agregado para esa hora, borrar las filas crudas es siempre correcto.

Tests de integración (PostgreSQL real)
  • Filas de más de 7 días → compactadas; filas recientes → intactas
  • Segunda ejecución → no duplica agregados ni pierde datos (idempotencia)
  • 3 horas distintas → 3 filas en worker_metrics_hourly
  • Solo datos recientes → sin agregados, sin borrados

Deuda técnica registrada para F3+

Insert en loop individual (T2.3) — suficiente para buffers de decenas de muestras. Si el buffer crece a miles, considerar pgx.CopyFrom.
Sin límite de tamaño de batch en el endpoint (T2.3) — no es problema con el agente (buffer acotado), pero a tener en cuenta si el endpoint se expone a más clientes.
AGENT_ADMIN_KEY en el agente (T2.6) — el agente necesita el admin key solo para el registro inicial. Si en el futuro se quiere reducir privilegios, se añade un endpoint de registro con worker key.
Loop single-threaded en reporter.py (T2.7) — si collect() bloquea por lentitud del driver, el intervalo de 10s se desfasa. No es problema en F2; en F3+ podría justificar un thread separado.
Compactación sin ejecución al arrancar (T2.11) — el job corre cada 24h. Si la API ha estado caída días, la primera compactación se produce en el siguiente tick. Para backfill inmediato se puede añadir una llamada inicial en Run.
Usuario del servicio = $(whoami) (T2.9) — si el script se ejecuta como root, el agente corre como root. Inofensivo en homelab; deuda si se expande a más nodos.
