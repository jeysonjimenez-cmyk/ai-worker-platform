✅ 2026-06-15
▼

El problema que resuelve: sin estas acciones, operar significa hacer UPDATE jobs SET ... a mano en producción. Cancelar un pending y reintentar un error son las dos operaciones que el operador necesita y que no deben requerir psql.

Archivos modificados
  • api/internal/admin/store.go— AdminCancelJob (cancel cross-app; libera VRAM vía jobs.ReleaseVRAMReservation si el job estaba running) y AdminRetryJob (error → pending, limpia worker_id, started_at, error_msg, resetea retry_count = 0).
  • api/internal/admin/handler.go— Handlers CancelJob y RetryJob.
  • api/main.go— Registra POST /admin/jobs/{id}/cancel y POST /admin/jobs/{id}/retry con adminMW.
AdminCancelJob no dispara webhook

Es contexto admin, no contexto de app. El webhook_url sigue en el job, pero el operador no debe disparar el flujo del cliente al cancelar manualmente.

AdminRetryJob resetea retry_count = 0

Tras un retry manual, el scheduler automático de F1 puede volver a reintentar si el job falla de nuevo. Los jobs en error ya tienen vram_released = true (liberada en Complete/FailTimedOutJobs de F1), así que el retry no libera de nuevo — no hay doble liberación.

CORS bloqueaba el dashboard en navegador real

El dashboard cargaba pero toda llamada a /admin/* fallaba con No 'Access-Control-Allow-Origin' header is present. curl no dispara el preflight OPTIONS (es un mecanismo solo de navegador), así que el bug era invisible a la verificación previa — exactamente el gap que el runbook había marcado como NO VERIFICADO.

Archivos modificados (fix CORS)
  • api/main.go— Middleware withAdminCORS que envuelve todo el mux: para /admin/* setea Access-Control-Allow-Origin: *, métodos GET, POST, OPTIONS, headers X-Admin-Key, Content-Type, y responde 204 al preflight OPTIONS sin requerir auth. Handler: mux → Handler: withAdminCORS(mux).
  • api/integration_test.go— buildServer envuelve con withAdminCORS(mux); añade TestAdmin_CORS_PreflightAndHeaders (preflight 204 sin auth; GET autenticado lleva el header; rutas no-admin no llevan CORS).
Por qué envolver el mux completo (Go 1.22+)

http.ServeMux devuelve 405 automáticamente para OPTIONS sobre un patrón registrado solo con GET/POST, antes de correr cualquier middleware atado al handler. El CORS tenía que interceptarse antes del routing — no dentro de cada handler.

Access-Control-Allow-Origin: * es seguro aquí

La auth de /admin/* es por header (X-Admin-Key), no por cookies. Sin credenciales implícitas del navegador no hay riesgo de CSRF vía origen arbitrario — el wildcard es seguro.

Retrospectiva — aprendizajes clave

Lo que funcionó bien

  • withAdminCORS envolviendo el mux completo: un punto de intercepción antes del routing, solución mínima y correcta
  • No implementar SSE: el polling de 5s satisface todos los criterios con cero complejidad en la API
  • Verificación en navegador como paso separado, no asumida: marcar criterios como NO VERIFICADO permitió encontrar el CORS
  • Reusar el job 377e0e29 del corpus SSRF F4.5 para el e2e de retry: fixture real ideal, sin crear casos especiales
  • Admin key en sessionStorage: scope a la pestaña, sin cookies → el wildcard CORS queda seguro

Lo que aprendimos del sistema real

  • Detección de worker offline real: 93–129s, no <90s — el monitor añade hasta un tick de latencia (corregido a ≤70s)
  • curl y el navegador son clientes fundamentalmente distintos: curl no envía Origin ni hace preflight
  • El polling de 5s es invisible para el operador y suficiente — nunca se sintieron datos "viejos"
  • La pila del dashboard (T5.4–T5.6) fue más rápida que los endpoints de API; la complejidad real estuvo en deploy y verificación
  • El claim por long-polling es tan rápido que hubo que parar el worker para tener un pending estable y hacer clic en cancelar

Lo más difícil técnicamente

  • El bug de CORS solo aparece en navegador: 10 tests + múltiples curls verdes y el dashboard no funcionaba
  • Comportamiento de Go 1.22+: ServeMux responde 405 a OPTIONS antes de cualquier middleware del handler
  • VITE_API_URL es build-time: cambiarla no surte efecto hasta el próximo --build, no al reiniciar
  • La brecha "contrato API verificado" vs "funciona en navegador" es real y requiere una pasada distinta

Postura de producción al cerrar F5

  • Dashboard en http://100.106.192.45:3000 (Tailscale, no expuesto a internet)
  • Auth por admin key (X-Admin-Key), sin sistema de usuarios
  • withAdminCORS activo en la API para /admin/*
  • Worker offline detectado en ≤70s (timeout 60s, tick 10s)
  • Runbook SQL f4.5-ops-without-dashboard.md vigente como respaldo
