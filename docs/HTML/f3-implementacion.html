T3.1
Scaffold del paquete worker_base + configuración por entorno
Paquete Python con la interfaz execute(job, ctx), config por env vars, cliente HTTP y ciclo de vida base.
Desarrollo 3 h

▼

El problema que resuelve: cada worker de inferencia (whisper, ollama, tts) necesita lógica idéntica de registro, heartbeat, claim y fencing. Sin un scaffold, cada uno reimplementa lo mismo. worker_base lo resuelve una vez; los workers reales solo implementan execute().

  • workers/worker_base/api_client.py NEW— APIClient wrapeando httpx: register(), heartbeat(), claim(), complete(), report_progress(), log(); X-Admin-Key para registro, X-Worker-Key para todo lo demás
  • workers/worker_base/scaffold.py NEW— Scaffold(config, execute) con ciclo de vida completo: registro, heartbeat thread, claim loop, fencing, graceful shutdown
  • workers/tests/test_config.py NEW— 7 tests: errores en las 4 vars requeridas, JSON inválido en capabilities, config válida, trailing slash en URL
  • workers/tests/test_scaffold.py NEW— 9 tests base (crecerá a 24 con T3.2–T3.8)
  • workers/pyproject.toml— añadido httpx>=0.28.0; pytest>=8.0.0 en dev; testpaths = ["tests"]
Convenciones clave
Config fail-fast al arrancar

Variables requeridas (WORKER_API_URL, WORKER_KEY, WORKER_ADMIN_KEY, WORKER_ID) sin defaults silenciosos. Si alguna falta, el proceso termina con un mensaje de error claro antes de intentar conectar a la API.

WORKER_ID estable es condición de idempotencia

El registro usa ON CONFLICT (id) DO UPDATE en el servidor. La idempotencia solo se materializa si el worker siempre se registra con el mismo id. UUID nuevo por arranque = una fila por boot. WORKER_ID viene de configuración estable; nunca se genera en runtime.

T3.3
Heartbeat en thread separado del loop de inferencia
Hilo dedicado que envía heartbeat cada N segundos, independiente de execute(). Un job largo no provoca falsos timeouts.
Desarrollo 3 h
✅ 2026-06-13
▼

El problema que resuelve: el monitor de F1 marca un worker como offline si no recibe heartbeat en 90s. Si el heartbeat estuviera en el mismo thread que execute(), un job largo de inferencia (whisper procesando 30 min de audio) bloquearía el heartbeat y el worker sería marcado offline incorrectamente.

Implementación
  • workers/worker_base/scaffold.py— _heartbeat_loop(): daemon thread dedicado; usa threading.Event.wait(interval) — espera el intervalo O hasta que _stop se active (permite shutdown limpio sin esperar el próximo tick); errores individuales se logean y reintentan sin terminar el thread
Tests añadidos
  • test_heartbeat_fires_while_execute_blocked: ≥2 heartbeats llegan mientras execute() duerme 2.5s con intervalo de 1s
  • test_heartbeat_survives_individual_failure: el primer heartbeat lanza excepción y el segundo llega correctamente
Verificado en hardware real (T3.12)
  • Cadencia real ~10s durante un execute() bloqueado 30s → worker permanece online ✅
T3.4
Claim loop con long-poll y backoff exponencial
Loop principal: POST /workers/{id}/claim?wait=N con backoff 1s→max. Al recibir job invoca execute(); sin job espera antes de reintentar.
Desarrollo 3 h
✅ 2026-06-13
▼

El problema que resuelve: el worker necesita consumir jobs de forma continua y tolerante a fallos de red, sin martillar la API cuando no hay trabajo. El endpoint de claim implementa long-poll genuino vía ?wait=N (LISTEN jobs_channel + WaitForNotification con deadline).

Comportamiento del loop
  • workers/worker_base/scaffold.py— _run_claim_loop(): 200 → parse job + execute() + _complete_job(); 204 → sin job, _stop.wait(2) antes de reintentar; error de red → backoff exponencial (1s → 2s → … → max), se resetea con cualquier respuesta HTTP; 4xx/5xx → log error + _stop.wait(5); excepción en execute() → complete con error=str(exc), worker sigue vivo
Tests añadidos
  • test_claim_loop_calls_execute_and_complete: claim → execute → complete end-to-end (API mockeada)
  • test_claim_loop_retries_on_network_error: primer claim lanza excepción, segundo claim funciona
  • test_execute_error_reported_as_complete_error: execute lanza ValueError → complete recibe error= con el mensaje; worker sigue vivo
T3.5
Manejo de fencing (409) en el reporte de resultados
Si la API responde 409 al completar un job, el scaffold descarta el resultado y vuelve al claim loop. No crashea ni reintenta.
Desarrollo 2 h
✅ 2026-06-13
▼

El problema que resuelve: el fencing de F1 (WHERE worker_id = $reporter) puede devolver 409 si el worker perdió su job por timeout de heartbeat y otro worker lo retomó. El cliente debe respetar esto: descartar el resultado sin crashear ni sobreescribir el job del nuevo worker.

Qué se implementó
  • workers/worker_base/scaffold.py— _complete_job(): si POST /ai/jobs/{id}/complete devuelve 409, loggea warning explícito ("fencing: job X no longer owned by this worker — discarding result") y retorna sin reintentar; el claim loop continúa
Tests añadidos
  • test_fencing_409_discards_and_continues: 409 en complete → worker llega al segundo claim (sigue vivo)
  • test_fencing_409_does_not_retry: complete se llama exactamente una vez (sin reintento)
El fencing de F1 cubre un escenario de F3 no anticipado

El 409 construido en F1 para el "worker zombie que reaparece" es lo que hace seguro el caso borde del shutdown >90s: dos workers, mismo job, sin coordinación, sin corrupción de datos. Inversión de F1 cubriendo F3 gratis.

T3.8
Graceful shutdown ante SIGTERM
Al recibir SIGTERM (docker compose stop), el worker termina limpiamente. El job en curso se completa o vuelve a pending vía el monitor de heartbeat.
Desarrollo 3 h
✅ 2026-06-13
▼

El problema que resuelve: docker compose stop envía SIGTERM. Sin handler, el proceso ignora la señal y Docker espera 10s antes de hacer kill -9, dejando el job colgado en running. Con el handler, el worker se detiene limpiamente.

Implementación
  • workers/worker_base/scaffold.py— run() instala signal.signal(SIGTERM, _sigterm); _sigterm llama self._stop.set(); el job en curso termina normalmente; el heartbeat monitor re-encola el job en ≤90s si el worker sale antes de completarlo
Tests añadidos
  • test_sigterm_stops_worker_with_no_job: SIGTERM cuando idle → _stop.is_set() tras run()
  • test_sigterm_stops_worker_during_execute: SIGTERM con execute en curso → execute completa, worker sale limpio
Decisión clave: no hay endpoint "return to pending"

No existe ningún endpoint worker-facing que devuelva un job a pending. SIGTERM simplemente detiene el heartbeat y el claim loop. El monitor de heartbeat de F1 (RequeueTimedOutJob) re-encola el job en ≤90s — mismo mecanismo que verifica T3.12 al matar el contenedor mid-job. Menos mecanismo = más correcto.

Verificado en hardware real (T3.12)
  • Kill del contenedor mid-job → job vuelve a pending en 32s (límite 90s) ✅
  • Otro worker lo retoma y completa sin intervención ✅

Decisiones de diseño
network_mode: host para Tailscale

La forma más simple de dar al contenedor acceso a la interfaz tailscale0 del host. Alternativas (MACVLAN, red bridge) requieren configuración de redes en Docker sin aportar aislamiento útil en ialab (nodo privado). Si en F4+ un worker expone un puerto propio, revisar.

uv solo en build-time; runtime usa el venv directamente

PATH apunta al venv para que python resuelva al intérprete del venv sin invocar uv run, que resincronizaría dependencias (incluidas las de dev) al arrancar el contenedor.

required: false en env_file

docker compose build funciona sin el archivo de credenciales. El scaffold detecta las vars faltantes al arrancar y falla con mensaje claro. Separación correcta entre build-time y runtime.

Bugs encontrados y corregidos durante la corrida
Bug crítico: claim 500 por services nil

Con WORKER_CAPABILITIES={"echo": true} (sin el array services), caps.Services quedaba nil → json.Marshal(nil) → "null" → jsonb_array_elements_text(null) reventa con SQLSTATE 22023. Ningún test lo atrapó porque todos los workers de prueba siempre mandaban un services array. Corregido con guarda: len(caps.Services) == 0 → no job. Lección: los tests prueban el contrato que imaginaste; el hardware prueba el que escribiste.

API bindeada a 127.0.0.1 — misma que F2

El deploy del VPS publicó la API en loopback; ialab no la alcanzaba por Tailscale. Exactamente el mismo problema que la retro de F2 documentó como aprendizaje. La regla "los servicios cross-node se ligan a la IP Tailscale" quedó en una retro que no se releyó. Corregido en deploy/vps/docker-compose.yml + docs/PORTS.md.

env_file en /etc/ exige root en ialab

El usuario de ialab no puede escribir en /etc/ai-platform/ sin sudo. Añadido fallback a ~/.config/ai-platform/worker-echo.env (user-writable) en el compose.

docker compose restart no re-lee env_file

Reutiliza la config del contenedor anterior. Para aplicar cambios de entorno hay que docker compose up -d (recrea el contenedor). El escenario 3 usó up -d. Documentado como nota operativa.

Retrospectiva — aprendizajes clave

Lo que funcionó bien

  • execute(job, ctx) como única superficie: worker-echo en ~10 líneas sin tocar HTTP
  • threading.Event para ciclo de vida: 24 tests del scaffold sin red ni servidor
  • No agregar endpoint "return to pending": heartbeat monitor de F1 lo cubre gratis
  • unnest($1::text[]) en IngestLogs: insert atómico del batch en una query
  • network_mode: host + required: false: build sin credenciales, fallo claro al arrancar

Lo más difícil técnicamente

  • Razonar el graceful shutdown como problema distribuido, no como código
  • Aceptar que execute() no es interrumpible es correcto (fencing cubre el caso borde)
  • signal.signal() solo desde el hilo principal → tests usan os.kill(os.getpid(), SIGTERM)
  • Packaging Docker con uv: build backend innecesario, __main__.py es la solución

Lo que tomó más tiempo

  • Plomería Docker con uv: tool.uv.package requiere build backend → revertir a __main__.py
  • Defecto silencioso del Makefile desde F1: make deploy no reconstruía la imagen Go
  • E2E en hardware: 4 correcciones para pasar de "todo listo" a "4/4 verde"
  • Patrones de F2 que se repiten: bind a 127.0.0.1, plomería de entorno en ialab

Riesgos que pasan a F4

  • Regla "bind a IP Tailscale" no codificada → se repitió igual que en F2
  • Validar capabilities en el registro, no solo en el claim (bug del services nil)
  • Ledger usa piso vram_total - 500 MB: overhead SO/drivers ~1.7 GB supera margen
  • httpx sin cliente persistente: evaluar si la frecuencia de logs sube en F4 (whisper)
  • upload_file_metadata() + job_files deferido a F4 (whisper produce archivos)

Deuda técnica registrada para F4+

Bug del claim con services nil — test pendiente — el fix usa guarda len(caps.Services) == 0, pero el caso services ausente/vacío no está cubierto por tests. También falta validar el shape de capabilities en el registro, no solo en el claim.
Regla "bind a IP Tailscale" sin codificar — se repitió exactamente como en F2. Convertirla en check del deploy o regla explícita verificable en docs/PORTS.md, no en la memoria de una retro.
Margen VRAM del ledger (VRAMMarginMB=500) — el overhead real del SO/drivers en ialab es ~1.7 GB > 500 MB. Whisper (F4) es el primer worker que reserva VRAM real; revisar el margen al integrar el primer model pesado.
httpx sin cliente persistente (conexión por llamada) — para echo es irrelevante. Si la frecuencia de log() sube en F4 (whisper puede emitir muchas líneas durante la transcripción), evaluar httpx.Client persistente.
upload_file_metadata() + job_files deferido — whisper produce archivos (VTT/SRT/JSON); el helper y el endpoint no existen aún. Se implementa en F4 junto con el servidor de archivos y el proxy del VPS (alcance ya previsto en el plan).
Bootstrap del worker sin automatizar — obtener WORKER_KEY registrando con ADMIN_KEY sigue siendo manual. Misma deuda que el agente (retro F2 #3). Post-MVP si no se agregan nodos.
Ruta de runtime de workers sin definir — doc con placeholder <repo>/deploy/ialab/...; inconsistente con /opt/ai-platform del agente. Definir al desplegar el primer worker pesado en F4.
worker-echo demasiado rápido para demos de timing — el runbook e2e requiere meter time.sleep(30) a mano para ver el escenario de heartbeat con execute bloqueado. Añadir un modo "slow-echo" o job de prueba con sleep configurable antes de F4.
