T7.1
Validación de conflicto vram_total_mb en el registro de workers
Si un segundo worker declara un vram_total_mb diferente para la misma GPU, la API retorna 409 — protege el ledger de corrupciones silenciosas que en F6 casi anulan toda la seguridad anti-OOM.
Desarrollo · API Go 3 h
✅
▼

El problema que resuelve: en F6 el env del worker declaraba 24564 MiB para una GPU de 15946 — el ON CONFLICT DO UPDATE silencioso habría sobrescrito el techo y el ledger permitiría reservar 24 GB sobre 16. La solución: pre-check antes del UPSERT; si difiere, 409 antes de tocar la tabla.

Archivos modificados
  • api/internal/workers/store.go— ErrVRAMConflict struct; Register(): SELECT vram_total_mb FROM gpus WHERE id = $1 antes del UPSERT; ON CONFLICT DO UPDATE SET hostname = EXCLUDED.hostname (ya no actualiza vram_total_mb).
  • api/internal/workers/handler.go— errors.As(err, &vramErr) → 409 con mensaje que incluye gpu_id, MiB del ledger y MiB declarados.
  • api/integration_test.go— TestWorkerRegister_VRAMConflict_Rejected: registra con 15946, verifica que 24564 → 409, ledger no corrompido, re-registro con mismo valor es idempotente.
Pre-check + UPSERT en dos pasos, no un UPSERT condicional

Una sola sentencia SQL INSERT … ON CONFLICT DO UPDATE WHERE EXCLUDED.vram = existing.vram no retorna ninguna fila si el conflicto falla la condición — no distingue "conflicto de vram" de "key no existe". El pre-check hace el flujo legible y el error explícito sin magia SQL.

La exclusión mutua emergió de la física, no del diseño

El plan original esperaba tres modelos simultáneos. La medición real reveló que TTS solo puede correr solo. El ledger implementa la exclusión mutua automáticamente: un job de TTS requiere 14720 MiB y el ledger bloquea cualquier otro claim hasta que se libere. Sin calibración este hallazgo habría sido un OOM en producción.

Tercer worker permanente. Reusa worker_base; llama al endpoint HTTP de Higgs, sube el WAV al file-server, reporta job_files. El idle-unload es docker stop (no endpoint del motor — SGLang-Omni no tiene /flush_cache).

Archivos creados

Archivos modificados
  • deploy/ialab/docker-compose.yml— Servicio worker-tts con /var/run/docker.sock montado; env_file worker-tts.env; volumen compartido con el file-server.
  • deploy/ialab/worker-tts.env.example NEW— Plantilla de env con HIGGS_URL, MIN_VRAM_TTS_MB, WORKER_ID.
  • workers/pyproject.toml— Script worker-tts = "worker_tts:main".
docker stop como mecanismo de unload — decisión deliberada

SGLang-Omni retorna 404 en /flush_cache. No existe API de shutdown del modelo. La única forma de liberar 14720 MiB es detener el container. El worker monta /var/run/docker.sock y llama docker stop ialab-higgs-tts-1 inmediatamente tras cada job — sin idle timeout (no tiene sentido con un modelo que ocupa toda la VRAM útil). Esto le da privilegios de Docker al container, decisión de seguridad consciente documentada.

Unload inmediato, no idle timeout

Con whisper (idle 300s) y ollama (idle 600s), mantener el modelo caliente acelera el segundo job. Con TTS ocupa 14720 MiB — mantenerlo caliente bloquea cualquier otro modelo. El unload tras cada job es la política correcta aunque el segundo job tarde un poco más.

Bug 1 — SSRF bloqueaba audio en loopback

Worker-whisper tiene una política SSRF que bloquea (1) esquema http:// y (2) rango 100.64.0.0/10 (Tailscale). Video Crack sirve los archivos de audio en http://127.0.0.1:8000 — bloqueado por el primer criterio. Fix: ALLOW_HTTP_AUDIO=1 en ~/.config/ai-platform/worker-whisper.env + --force-recreate.

Bug 2 — Parseo del resultado de traducción fallaba con dict

result.get("result") devuelve un dict {"result": "1. texto..."}, no un string. En both mode este path nunca se usaba para construir subtítulos primarios. Fix: isinstance(job_result, dict) antes del .strip().

Bug 3 — TTS se encadenaba automáticamente después de traducción

La implementación inicial de T7.7 llamaba a _run_dub() automáticamente en _process() cuando TTS_MODE=platform. El usuario esperaba que TTS solo corriera al presionar "Doblar audio". Fix: bloque auto-chain eliminado de _process().

Todos los bugs eran latentes en both mode — el modo de validación oculta sistemáticamente los defectos de integración hasta que se hace el switch definitivo. Esta es la observación más importante de la fase.

Semántica por-job del ledger — decisión documentada retroactivamente

La reserva de VRAM se ata al ciclo de vida del job, no del modelo cargado. Un modelo caliente entre jobs mantiene su reserva en el ledger. Esto es correcto y deliberado, pero no estaba documentado en DESIGN.md. T7.14 lo formaliza para que futuros lectores entiendan por qué vram_reserved_mb=0 con un modelo caliente es una deriva de diagnóstico, no el estado normal.

Retrospectiva — aprendizajes clave

Lo que funcionó bien

  • Calibrar VRAM en el timebox (T7.2) antes de escribir el worker: 2000 → 14720 MiB; sin medición → OOM en producción
  • El ledger implementó exclusión mutua automáticamente sin código especial: es una propiedad emergente de la física
  • El patrón de tres flags (legacy/platform/both) absorbió todos los bugs de integración antes del switch sin afectar producción
  • Escucha manual como criterio formal de calidad de audio — pragmático y no falsificable con métricas de señal

Lo que aprendimos del sistema real

  • both mode oculta sistemáticamente los bugs de integración — todos los defectos de T7.13 eran invisibles en both
  • SGLang-Omni no tiene /flush_cache: docker stop es el único mecanismo de unload — docker.sock como dependencia explícita
  • ALLOW_HTTP_AUDIO=1 necesario cuando cliente y worker comparten el mismo nodo (loopback + SSRF policy)
  • El contrato de client.wait() devuelve un dict en result, no un string — no estaba documentado

Lo que más sorprendió

  • El valor teórico de VRAM de TTS (2000) estaba 7× por debajo del real (14720) — la calibración empírica es mandatoria
  • Tres bugs de video-crack latentes durante meses solo se volvieron visibles en el switch a platform — el flip reveló la deuda de integración acumulada
  • El proceso viejo de uvicorn seguía vivo con TRANSCRIBE_MODE=both mientras el archivo ya decía platform — verificar el env del proceso, no del archivo
  • El job japonés fue el primero que ejercitó el nuevo path de parseo de traducción — reveló el bug que todos los otros videos habían enmascarado
