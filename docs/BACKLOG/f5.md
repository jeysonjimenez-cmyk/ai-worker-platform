# Backlog — Fase 5: Dashboard mínimo

> Fuente única: IMPLEMENTATION_PLAN.md v1.2, Fase 5 · Duración estimada: ~3 días (solapable con F4.5) · Complejidad: Baja
> Arquitectura congelada (DESIGN.md v1.4): no introducir componentes ni tecnologías fuera de esta lista. React + Vite y la autenticación por API key de admin ya están definidos en DESIGN.md §"Dashboard web".
> Insumo operativo: retrospectivas F0–F4.5 (riesgos reales observados). Orden cronológico de ejecución. Tareas de 1–4 h.

> **Decisión de implementación:** el dashboard es **lo mínimo para operar producción sin `psql`**. Una sola vista (workers + jobs por estado), detalle de job, y dos acciones (cancelar `pending`, reintentar `error`). Polling cada 5s. La lista "explícitamente fuera" (SSE, gráficas, costos, métricas históricas, filtros avanzados) **es parte del entregable**: todo lo que esté ahí se rechaza hasta F11.

## 1. Objetivo de F5 (según el plan)

Lo mínimo para operar producción sin `psql`: ver estados y actuar sobre jobs. Nada más — el plan es explícito en que "los dashboards son agujeros negros de tiempo y Video Crack no necesita métricas para generar valor". Concretamente:

- **React + Vite servido desde el VPS**, autenticado con la API key de admin (DESIGN.md §"Autenticación del dashboard": misma key de admin, sin sistema de usuarios).
- **Una vista**: workers (online/offline/busy + job en curso) + jobs por estado (pending/running/done/error).
- **Detalle básico de job**: payload, error, worker asignado.
- **Acciones**: cancelar job pendiente, reintentar job en error — se mantienen porque sin ellas operar significa hacer `UPDATE jobs SET ...` en producción.
- **Actualización por polling cada 5s** (sin SSE — el tiempo real se va a F11 junto con el streaming de logs).

**Criterios de aceptación de la fase (plan):** los workers offline se distinguen en <90s sin refrescar manualmente; cancelar y reintentar funcionan desde la UI; se puede diagnosticar un job fallido (ver error y payload) sin tocar la base de datos.

**Explícitamente fuera (→ F11), parte del entregable:** SSE, gráficas de GPU/VRAM, filtros avanzados, métricas históricas, vista de costos.

## T5.1 — API: endpoints admin de lectura (list workers, list jobs por estado, detalle de job)

**Tipo:** Desarrollo · **Esfuerzo:** 4 h · **Dependencias:** F1, F2

**Descripción:** Agregar la superficie de **lectura** que el dashboard necesita, autenticada con la API key de admin (`adminMW`, ya existe desde F1 — hoy solo lo usa `POST /workers/register`). No existen endpoints de listado ni un detalle cross-app; los actuales (`GET /ai/jobs/{id}` con `X-App-Key`) son app-scoped. Endpoints mínimos:
- `GET /admin/workers` → lista de workers con `status` (online/offline/busy), `current_job_id`, `gpu_id`, `last_heartbeat`. El estado offline lo fija el monitor de heartbeat de F1 (≤90s); el endpoint solo lo refleja.
- `GET /admin/jobs?status=<pending|running|done|error>` → lista de jobs filtrable por estado, con los campos que la vista necesita (id, service, app, status, worker_id, priority, created_at, workflow_id). Orden por `created_at` desc, con un límite razonable (sin paginación avanzada — eso es F11).
- `GET /admin/jobs/{id}` → detalle: payload, error, worker asignado, retry_count/max_retries, timestamps. **No serializa `vram_released` ni campos internos del ledger** (R1).

Reusar las funciones de store existentes donde aplique (p.ej. `jobs.Get`) y agregar solo las queries de listado faltantes. Nada de agregaciones ni métricas (F11).

**Criterios de aceptación:**
- [x] `GET /admin/workers` con `X-Admin-Key` válida devuelve todos los workers con su estado y job en curso; sin la key → 401.
- [x] `GET /admin/jobs?status=error` devuelve solo los jobs en `error`; sin filtro devuelve todos (con límite), ordenados por `created_at` desc.
- [x] `GET /admin/jobs/{id}` devuelve payload, error y worker asignado; **no** incluye `vram_released` ni otros campos internos del ledger (R1).
- [x] Los endpoints son cross-app (admin ve jobs de cualquier app), a diferencia de `GET /ai/jobs/{id}` que es app-scoped.

**Resultado esperado:** El dashboard tiene de dónde leer el estado completo del sistema con la admin key, sin tocar la base de datos.

## T5.2 — API: acciones admin (cancelar `pending`, reintentar `error`)

**Tipo:** Desarrollo · **Esfuerzo:** 3 h · **Dependencias:** T5.1

**Descripción:** Las dos acciones que el plan exige para no operar con `UPDATE jobs SET ...` a mano, autenticadas con admin key:
- `POST /admin/jobs/{id}/cancel` → cancela un job `pending` (admin, cross-app). Reusa la transición de cancel ya implementada en F1, incluyendo la liberación de reserva de VRAM vía `ReleaseVRAMReservation` si correspondiera.
- `POST /admin/jobs/{id}/retry` → **nuevo**: reencola un job en `error` (terminal). El retry actual es automático y solo dentro de `max_retries`; esto es un retry **manual** de un job que ya agotó sus reintentos o falló de forma terminal. Transiciona `error → pending`, limpia `worker_id`, `started_at`, `error_msg` y resetea `retry_count`. La VRAM ya fue liberada al entrar en `error` (F1), así que no hay doble liberación. Rechazar el retry sobre jobs que no estén en `error` (409/400 claro).

**Criterios de aceptación:**
- [x] `POST /admin/jobs/{id}/cancel` sobre un job `pending` lo transiciona a cancelado; sobre un job ya terminal → error claro (no corrompe estado).
- [x] `POST /admin/jobs/{id}/retry` sobre un job en `error` lo devuelve a `pending`, listo para ser reclamado por un worker; el job vuelve a aparecer en la cola.
- [x] `retry` sobre un job que no está en `error` (p.ej. `running` o `done`) es rechazado con un código y mensaje claros.
- [x] Ninguna acción produce doble liberación de VRAM ni deja el ledger inconsistente (reusa los caminos centralizados de F1).

**Resultado esperado:** Operar (cancelar/reintentar) desde la API admin, base de las dos acciones de la UI, sin SQL manual en producción.
