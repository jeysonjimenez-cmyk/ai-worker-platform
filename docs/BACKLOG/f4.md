>
> **Decisión de implementación:** `worker-whisper` (faster-whisper, CUDA, concurrency 1) sobre el scaffold `worker_base` de F3. El worker real solo implementa `execute(job, ctx)`; el ciclo de vida (registro, heartbeat, claim, fencing, shutdown) ya lo resuelve el scaffold.

---

## Objetivo de F4 (según el plan)

Transcripción real end-to-end —el servicio principal de Video Crack— corriendo en producción: `POST /ai/jobs` con `service: transcription` y un audio de **1 hora** → `done` con VTT descargable vía un proxy en el VPS. Valida el contrato completo con un **modelo pesado (10 GB VRAM)** y **jobs largos** (donde heartbeat, timeouts y reintentos pensados para jobs cortos pueden interactuar mal). Introduce el almacenamiento y servidor de archivos en ialab y su proxy en el VPS.

## T4.1 — Esqueleto de `worker-whisper` sobre el scaffold (CUDA, concurrency 1)

**Tipo:** Desarrollo · **Esfuerzo:** 4 h · **Dependencias:** F3

**Descripción:** Crear el paquete `worker_whisper/` que implementa `execute(job, ctx)` sobre `worker_base`. Dockerfile con base CUDA (faster-whisper requiere GPU) reutilizando el patrón de F3. Entrada en `deploy/ialab/docker-compose.yml`. Registro con `capabilities = {"services":["transcription"], "cuda": true, "vram_total_mb": <real>}`. `execute()` inicialmente devuelve un stub para validar el ciclo claim→execute→complete con el modelo aún sin cargar.

**Criterios de aceptación:**
- [x] `docker compose build` produce la imagen CUDA con dependencias congeladas (`uv.lock`).
- [x] El worker se registra con `service: transcription` y aparece `online` en la tabla `workers`.
- [x] Reclama un job de `transcription` y completa el ciclo con un `execute()` stub (sin transcribir aún).
- [x] El `env_file` sigue el patrón de F3 (fallback a `~/.config/ai-platform/`, credenciales fuera de la imagen).

**Resultado esperado:** Worker whisper desplegable en ialab que participa del ciclo de jobs; base para colgar la transcripción real.

## T4.2 — Descarga de `audio_url` con validación SSRF + límite de tamaño

**Tipo:** Seguridad · **Esfuerzo:** 3 h · **Dependencias:** T4.1

**Descripción:** En el worker, descargar el `audio_url` del payload aplicando las **mismas reglas SSRF de F1** (solo `https://`, bloqueo de RFC 1918 y `100.64.0.0/10`) y un límite de tamaño configurable. Rechazar antes de descargar si la URL no pasa; abortar la descarga si excede el límite. Sin tecnología nueva (reusa la política ya definida en F1, implementada en Python para el lado worker).

**Criterios de aceptación:**
- [x] Una `audio_url` `http://` o hacia IP privada/`100.64.0.0/10` → el job falla con error claro, sin intentar la descarga.
- [x] Un archivo que excede el límite de tamaño → descarga abortada + error claro.
- [x] Una `audio_url` `https://` válida y dentro del límite → descarga exitosa a disco local del worker.
- [x] Test unitario de la validación SSRF con casos permitidos y bloqueados.

**Resultado esperado:** El worker solo descarga audio de fuentes seguras y acotadas, con la misma política que el webhook dispatcher de F1.

## T4.3 — Endpoint de registro en `job_files` + helper `upload_file_metadata()`

**Tipo:** Desarrollo · **Esfuerzo:** 3 h · **Dependencias:** F1, F3 (deferido de F3)

**Descripción:** Endpoint en la API Go para que un worker registre metadata de un archivo de salida, autenticado con worker key y con **fencing** (`WHERE worker_id = $reporter`, 409 si no coincide). Escribe en `job_files` (tabla ya existe desde F1). Añadir el helper `upload_file_metadata()` al scaffold (deferido de F3). No incluye el servidor ni el contenido del archivo —solo la metadata.

**Criterios de aceptación:**
- [x] Un POST válido de un worker dueño del job inserta una fila en `job_files` (job_id, filename, tamaño, etc.).
- [x] Worker no dueño → 409 (fencing); sin worker key → 401; payload inválido → 422.
- [x] `ctx.upload_file_metadata(...)` en el scaffold llama el endpoint y maneja 409 como los demás helpers (descarta + log).
- [x] Test de integración contra PostgreSQL real (testcontainers, sin mocks de DB).

**Resultado esperado:** Los workers registran sus archivos de salida en la DB; insumo del servidor de archivos (T4.6) y del proxy (T4.7).

## T4.4 — Transcripción real con progreso por segmentos + salida VTT/SRT/JSON

**Tipo:** Desarrollo · **Esfuerzo:** 4 h · **Dependencias:** T4.2, T4.3

**Descripción:** Implementar `execute()` con faster-whisper: transcribe el audio descargado, reporta **progreso real** (% por segmentos vía `ctx.report_progress()`), escribe las salidas VTT/SRT/JSON en `files/{job_id}/...` en ialab y registra cada archivo con `ctx.upload_file_metadata()`. Concurrency 1 (un job a la vez por worker).

**Criterios de aceptación:**

- [x] El progreso reportado avanza de forma realista durante la transcripción (no salta de 0 a 100).
- [x] La salida VTT es válida y descargable (verificable en T4.7).
- [x] Dos jobs de transcripción encolados se procesan **en serie** (concurrency 1).

**Resultado esperado:** Transcripción real produciendo subtítulos descargables, con progreso fiel al avance del job.

## T4.5 — Gestión de modelo: carga lazy + descarga por inactividad

**Tipo:** Desarrollo · **Esfuerzo:** 3 h · **Dependencias:** T4.4

**Descripción:** El modelo whisper se carga al **primer job** (no al arrancar el worker) y se descarga tras **10 min de inactividad**, llamando al endpoint existente `POST /workers/{id}/unload-model` para **liberar la reserva del ledger** (`ReleaseModelVRAM`, ya implementado en F1). Reutiliza el endpoint; no se crea uno nuevo.

**Criterios de aceptación:**
- [x] Primer job tras arrancar → el modelo se carga (VRAM sube, verificable en métricas del agente).
- [x] Tras 10 min sin jobs → el modelo se descarga y el worker llama `unload-model`; `gpus.vram_reserved_mb` vuelve a bajar.
- [x] Un job nuevo tras la descarga → el modelo se recarga solo.
- [x] La descarga no interrumpe un job en curso (solo aplica en inactividad).

**Resultado esperado:** La VRAM del modelo se libera cuando no se usa, dejando lugar a otros workers (relevante para la convivencia de F6), sin intervención.

## T4.6 — Servidor de archivos en ialab (bind a IP Tailscale)

**Tipo:** Infraestructura · **Esfuerzo:** 3 h · **Dependencias:** T4.4

**Descripción:** Servidor HTTP simple en ialab que sirve `files/{job_id}/...` en un puerto interno. **Bind explícito a la IP Tailscale de ialab** (`100.103.55.110`), nunca `127.0.0.1` ni `0.0.0.0` — lección recurrente de F2/F3: los servicios cross-node se ligan a la IP Tailscale. Solo alcanzable desde el VPS (ACLs del tailnet).

**Criterios de aceptación:**
- [x] `ss -tlnp` en ialab muestra el servidor escuchando en la IP Tailscale configurada, no en `127.0.0.1` ni `0.0.0.0`.
- [x] `curl` desde el VPS a `http://100.103.55.110:<puerto>/files/{job_id}/<archivo>` (vía Tailscale) devuelve el contenido.
- [x] El servidor no es alcanzable desde internet público.
- [x] El puerto queda registrado en `docs/PORTS.md`.

**Resultado esperado:** Los archivos de salida de los jobs son servibles desde ialab hacia el VPS por la red privada, sin exposición pública.

## T4.7 — Proxy de archivos en la API Go (streaming + 503)

**Tipo:** Desarrollo · **Esfuerzo:** 4 h · **Dependencias:** T4.6

**Descripción:** Endpoint `GET /ai/jobs/{id}/files/{filename}` en la API Go que hace proxy al servidor de archivos de ialab vía Tailscale. **Streaming, sin bufferizar en memoria** (los archivos pueden ser grandes). Si ialab está offline, responde **503 con mensaje claro**, no un error genérico.

**Criterios de aceptación:**
- [x] Un GET de un archivo existente → 200 con el contenido vía streaming (sin cargar el archivo entero en memoria del VPS).
- [x] Con ialab apagado → 503 con mensaje claro (no 500 ni timeout colgado).
- [x] El filename se valida (no permite path traversal fuera de `files/{job_id}/`).
- [x] Autenticación de app (`X-App-Key`), consistente con el resto de endpoints `/ai/jobs/*`.

**Resultado esperado:** Una app descarga los resultados de un job a través del VPS sin conocer ni alcanzar ialab directamente, con degradación clara si el nodo está caído.

## T4.8 — Timeout máximo por job, configurable por service

**Tipo:** Desarrollo · **Esfuerzo:** 3 h · **Dependencias:** T4.4

**Descripción:** En la API, un timeout máximo de ejecución por job, **configurable por service** (los videos largos de Video Crack lo van a necesitar). Un job `running` que excede su timeout máximo se trata como fallo (libera VRAM y reintenta/marca error según la lógica de F1). Distinto del heartbeat (90s): este acota la duración total, no la ausencia de señal.

**Criterios de aceptación:**
- [x] Un job que supera el timeout máximo de su service → pasa a error/reintento, liberando la reserva de VRAM (vía `ReleaseVRAMReservation`).
- [x] El timeout es configurable por service (un audio de 1 h no debe dispararlo; el valor de `transcription` lo contempla).
- [x] Un job dentro de su timeout no se ve afectado.
- [x] Test de la transición de timeout (job sembrado que excede el límite).

**Resultado esperado:** Un job atascado tiene un techo de duración y no consume VRAM indefinidamente, sin afectar a los jobs largos legítimos.

## T4.9 — Calibración de `min_vram_mb` real de whisper + verificación del piso del ledger

**Tipo:** Desarrollo · **Esfuerzo:** 3 h · **Dependencias:** T4.5 (retro F3 / F2 #1)

**Descripción:** Medir la VRAM real que consume whisper con el modelo cargado (vía métricas del agente / `nvidia-smi` durante un job) y fijar `serviceRequirements["transcription"]` (hoy `10000`, valor teórico) al valor medido. Verificar que el piso efectivo del claim (`vram_total_mb - VRAMMarginMB`, hoy margen 500 MB) es consistente con el `vram_free_mb` real reportado por el agente (la alerta de deriva de T2.10 es el insumo). Ajustar el margen solo si la medición lo exige para `transcription`; **no** reemplazar el ledger por `vram_free_mb` (reintroduciría la carrera que el ledger previene).

**Criterios de aceptación:**
- [x] `min_vram_mb` de `transcription` refleja la VRAM medida del modelo, no el valor teórico.
- [x] El claim de un job de transcripción reserva la VRAM medida y la libera al completar (verificable en `gpus.vram_reserved_mb`).
- [x] No hay warning de deriva (T2.10) injustificado con whisper cargado y un job corriendo, dentro del margen configurado.
- [x] El cambio de margen (si lo hubo) queda documentado con el valor medido y su razón.

> Los 4 criterios dependen de hardware real (ialab). El código de soporte ya está implementado: `MIN_VRAM_TRANSCRIPTION_MB` sobreescribe `serviceRequirements["transcription"]` y `VRAM_MARGIN_MB` sobreescribe el margen; el piso del ledger se verifica en `TestVRAMLedgerPiso_MarginRespected`.

**Resultado esperado:** El ledger refleja el consumo real de whisper, base correcta para la convivencia de modelos de fases posteriores.
