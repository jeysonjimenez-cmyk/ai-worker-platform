# Backlog — Fase 4.5: SDK mínimo + Video Crack transcribe en producción

> Fuente única: IMPLEMENTATION_PLAN.md v1.2, Fase 4.5 · Duración estimada: 1 semana · Complejidad: Media
> Arquitectura congelada (DESIGN.md v1.4): no introducir componentes ni endpoints fuera de esta lista.
> Insumo operativo: retrospectivas F0–F4 (riesgos reales observados). Orden cronológico de ejecución. Tareas de 1–4 h.
>
> **Decisión de implementación:** el primer consumidor real (Video Crack) entra en producción con el primer servicio real (transcripción), en **doble ejecución** (sistema viejo activo como respaldo, salidas comparadas). El SDK es mínimo: tres métodos, ningún método que Video Crack no use hoy. Lo específico de la app vive en la app; la plataforma solo gana endpoints genéricos.

---

## 1. Objetivo de F4.5 (según el plan)

El primer consumidor real entra en producción con el primer servicio real. A partir de aquí, todo requisito oculto de Video Crack (videos largos, formatos, operación) se descubre con **un solo servicio migrado, no con tres**. Concretamente:

- **SDK Python mínimo** (`client/` en el monorepo, versionado junto a la API): `create_job(service, payload, ...)`, `wait(job_id)` (polling con backoff + timeout), `download(job_id, filename, dest)`. Nada más.
- **Integración en Video Crack**: el flujo de transcripción usa el SDK detrás de un flag (viejo / plataforma / ambos), en doble ejecución con comparación de salidas.
- **API key de app** para Video Crack.
- **Documentación del contrato** con ejemplos reales (curl + SDK) — es el onboarding de futuras apps.

**Criterios de aceptación de la fase (plan):** Video Crack transcribe en producción vía plataforma con el sistema viejo como respaldo activo; el video más largo del catálogo real procesa sin intervención manual; un reinicio de ialab mid-job se recupera solo y Video Crack recibe su resultado; el SDK no contiene ningún método que Video Crack no use hoy.

## 3. Triage: qué se resuelve ahora y qué se pospone

**Se resuelven en F4.5 (bloquean el objetivo de la fase):**
- **R1 → T4.5.7**: confirmar/garantizar que Video Crack sirve audio por `https://` público. Sin esto la integración no transcribe nada.
- **R2 → T4.5.7**: quitar `ALLOW_HTTP_AUDIO` del env del worker en ialab antes de poner el primer cliente en producción. Endurecimiento de seguridad imprescindible para "entrar en producción".
- **R3 → T4.5.9**: monitoreo de VRAM real durante el procesamiento del corpus, como criterio de aceptación de la corrida de producción (no tarea aparte).
- **R4 → T4.5.8**: runbook mínimo de queries SQL operativas. Es la mitigación que el propio plan nombra; barato y reduce un riesgo real de operar sin F5.
- **R5**: se incorpora como **criterio de aceptación del SDK** (T4.5.2), no como tarea.

**Se posponen (valiosas pero no necesarias para el objetivo de F4.5):**
- **`deploy-ialab` / `rsync` automatizado a ialab** (retro F4 §3a, tabla de riesgos). F4.5 **no cambia código del worker** en ialab (el SDK vive del lado de la app; los ajustes de VRAM de R3 son env de la API en el VPS, vía `make deploy`). El gap del rsync no bloquea esta fase. Se mantiene como deuda de tooling para la próxima fase que modifique workers (F6).
- **Healthcheck de env vars críticas al arrancar la API / verificación de disco en el build** (retro F4 §3b–d). Mejoras de robustez del build de workers; no hay build de worker nuevo en F4.5.
- **Bootstrap automatizado del worker / `httpx.Client` persistente** (retros F2/F3). Sin impacto en el objetivo de esta fase; post-MVP.
- **F5 (dashboard)** es solapable con F4.5 pero es su propia fase; aquí solo se cubre la mitigación de R4 (runbook), no la UI.

> **Fuera de alcance de F4.5** (no crear tareas): dashboard (F5), traducción/`worker-ollama` y test de convivencia (F6), TTS (F7), budgets/`max_daily_usd` *enforcement* y API workers externos (F9), cualquier cuarto método del SDK no usado hoy por Video Crack.

## T4.5.2 — SDK Python mínimo: `create_job` + `wait` + `download`

**Tipo:** Desarrollo · **Esfuerzo:** 4 h · **Dependencias:** F4

**Descripción:** Crear el paquete `client/` (Python 3.12 + uv, versionado junto a la API). Tres métodos y nada más:
- `create_job(service, payload, *, priority=None, requirements=None, routing=None, webhook_url=None)` → `POST /ai/jobs` con header `X-App-Key`, devuelve el `job_id`.
- `wait(job_id, *, timeout=None, interval=...)` → polling de `GET /ai/jobs/{id}` con **backoff** hasta estado terminal (`done`/`error`), respetando `timeout`; reusa el patrón de backoff ya probado en el agente (retro F2 §5).
- `download(job_id, filename, dest)` → `GET /ai/jobs/{id}/files/{filename}` (proxy de T4.7), escribe a `dest` por streaming (no carga el archivo entero en memoria).

Sin reintentos especulativos, sin caché, sin abstracción de "workflow": lo que Video Crack necesita hoy y nada más (R5).

**Criterios de aceptación:**
- [x] Los tres métodos existen y firman exactamente el contrato del plan; no hay un cuarto método público.
- [x] `create_job` envía `X-App-Key` y mapea `priority` string (`high`/`normal`/`low`) según el contrato de DESIGN.md.
- [x] `wait` corta por `timeout` con una excepción clara y hace backoff (no polling agresivo de intervalo fijo).
- [x] `download` escribe a disco por streaming y propaga el 503 del proxy (ialab offline) como error claro.
- [x] `client/` tiene `uv.lock` commiteado (versiones congeladas, convención del proyecto).

**Resultado esperado:** Un SDK que un consumidor real puede importar para crear, esperar y descargar un job de transcripción, sin tocar HTTP a mano.

## T4.5.5 — Integración de transcripción en Video Crack detrás de flag (viejo / plataforma / ambos)

**Tipo:** Desarrollo · **Esfuerzo:** 4 h · **Dependencias:** T4.5.3, T4.5.1

**Descripción:** Adaptar el flujo de transcripción de Video Crack para que use el SDK, detrás de un flag de tres posiciones: `legacy` (solo sistema viejo), `platform` (solo plataforma), `both` (doble ejecución: ambos corren, se conservan las dos salidas para comparar). El flag por defecto arranca en `both` para el período de validación. Lo específico de Video Crack (formatos de entrada, post-proceso de subtítulos) vive en Video Crack, no en la plataforma (R5).

**Criterios de aceptación:**
- [x] Con el flag en `legacy`, Video Crack se comporta exactamente como antes (sin tocar la plataforma).
- [x] Con el flag en `platform`, la transcripción se obtiene vía SDK y el sistema viejo no corre.
- [x] Con el flag en `both`, ambos sistemas producen su salida y ambas quedan disponibles para el comparador (T4.5.6).
- [x] El audio se entrega a la plataforma como `audio_url` `https://` público (cumple R1); ningún cambio degrada el SSRF del worker.

**Resultado esperado:** Video Crack puede transcribir vía plataforma con el sistema viejo como respaldo conmutable por flag, sin un salto al vacío.
