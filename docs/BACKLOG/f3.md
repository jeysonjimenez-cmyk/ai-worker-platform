## T3.2 — Registro del worker con capabilities al arrancar

**Tipo:** Desarrollo · **Esfuerzo:** 2 h · **Dependencias:** T3.1

**Descripción:** Al arrancar, el scaffold registra el worker en la API con sus capabilities/services declarados (endpoint `POST /workers/register` existente de F1). Registro idempotente: re-arrancar no duplica el worker ni rompe su estado.

**Criterios de aceptación:**
- [ ] Primer arranque → el worker aparece registrado con sus capabilities.
- [ ] Re-arranque del mismo worker → se re-registra sin duplicar (idempotente).
- [ ] Capabilities declaradas por entorno se persisten tal cual en el registro.

**Resultado esperado:** El worker se anuncia a la plataforma solo al arrancar, base para que el claim filtre por capabilities.

## T3.3 — Heartbeat en thread separado del loop de inferencia

**Tipo:** Desarrollo · **Esfuerzo:** 3 h · **Dependencias:** T3.2

**Descripción:** Hilo dedicado que envía heartbeat a la API cada intervalo configurado (`POST /workers/{id}/heartbeat` de F1), **independiente** del loop de inferencia. Garantiza que mientras `execute()` está bloqueado en un job largo, el worker no es marcado offline por el monitor de heartbeat de F1 (timeout 90s).

**Criterios de aceptación:**
- [ ] El heartbeat sigue llegando mientras `execute()` está bloqueado (test unitario con `execute()` que duerme más que el timeout, API mockeada).
- [ ] El hilo de heartbeat no muere si un heartbeat individual falla (loggea y reintenta en el siguiente intervalo).
- [ ] Al terminar el worker, el hilo de heartbeat se detiene limpiamente.

**Resultado esperado:** Un job largo no provoca falsos timeouts; el heartbeat es ortogonal a la inferencia.

## T3.4 — Claim loop con long-poll y backoff

**Tipo:** Desarrollo · **Esfuerzo:** 3 h · **Dependencias:** T3.2

**Descripción:** Loop principal del scaffold: pide trabajo al endpoint de claim de F1 (`POST /workers/{id}/claim`) con long-poll/backoff. Al recibir un job, invoca `execute(job)`, reporta el resultado vía complete. Sin job disponible → backoff antes de reintentar, sin martillar al VPS.

**Criterios de aceptación:**
- [ ] Con un job pendiente compatible, el loop lo reclama y llama a `execute()` (test con API mockeada).
- [ ] Sin jobs, el loop aplica backoff y no satura la API.
- [ ] Tras `execute()` exitoso, el job se marca `complete` vía la API.
- [ ] Un error de red en el claim no termina el proceso: reintenta con backoff.

**Resultado esperado:** El worker consume jobs de forma continua y tolerante a fallos transitorios, sin lógica de inferencia propia.

## T3.5 — Manejo de fencing (409) en el reporte de resultados

**Tipo:** Desarrollo · **Esfuerzo:** 2 h · **Dependencias:** T3.4

**Descripción:** Si la API responde 409 al reportar progreso o completar un job (el job ya no pertenece a este worker — fencing de F1, `WHERE worker_id = $reporter`), el scaffold descarta el resultado, lo loggea y vuelve al claim loop. No crashea ni reintenta el reporte.

**Criterios de aceptación:**
- [ ] Un 409 en `complete`/`progress` → resultado descartado + log explícito, el worker sigue vivo y vuelve a reclamar (test con API mockeada devolviendo 409).
- [ ] El worker no reintenta el reporte fenced ni sobreescribe el job de otro worker.

**Resultado esperado:** El fencing del servidor se respeta en el cliente: un worker que perdió su job (p. ej. por timeout de heartbeat) no corrompe el resultado del que lo retomó.

## T3.8 — Graceful shutdown ante SIGTERM

**Tipo:** Desarrollo · **Esfuerzo:** 3 h · **Dependencias:** T3.4

**Descripción:** Al recibir SIGTERM (p. ej. `docker compose stop`), el scaffold termina el job en curso si puede hacerlo a tiempo, o lo devuelve a `pending` para que otro worker lo retome — sin dejarlo colgado en `running`. Detiene el heartbeat y el claim loop limpiamente.

**Criterios de aceptación:**
- [x] SIGTERM sin job en curso → el worker sale limpio (heartbeat y loop detenidos).
- [x] SIGTERM con job en curso → el job se completa o vuelve a `pending`, nunca queda `running` huérfano (test con API mockeada y `execute()` en curso).
- [x] El proceso no ignora SIGTERM ni requiere `kill -9`.

**Resultado esperado:** Un `docker compose stop/restart` no pierde ni cuelga jobs; el ciclo de vida del job sobrevive al reinicio del contenedor.

## Ajustes posteriores a la revisión de supuestos (validados contra F1/F2)

> Revisión de los supuestos del backlog contra la implementación real de F1/F2. Ninguno cambia la arquitectura ni el alcance; son precisiones de comportamiento ya existente. Se agregan tras implementar T3.1–T3.5.

**Verificado — sin cambios necesarios:**

- **Registro idempotente (T3.2):** `POST /workers/register` es UPSERT real (`workers/store.go:74`, `ON CONFLICT (id) DO UPDATE`). No duplica en `docker restart`. El `api_key` **no** se modifica al re-registrar (re-arrancar conserva la credencial original).
- **Long-poll del claim (T3.4):** `POST /workers/{id}/claim` implementa long-poll genuino vía `?wait=N` (`handler.go:120` `claimWithWait` → `LISTEN jobs_channel` + `WaitForNotification` con deadline). Sin el parámetro, responde `204` de inmediato. La terminología del backlog es correcta.

**Ajuste a T3.2 — id de worker estable (la idempotencia depende del cliente):**

El `ON CONFLICT` es sobre `workers.id`. La idempotencia del servidor solo se materializa si **el worker se registra siempre con el mismo `id`**. El scaffold debe derivar el `id` de una fuente determinística (variable de entorno o hostname/servicio), **nunca** generar un UUID nuevo por arranque — eso crearía una fila por boot, justo la duplicación que el criterio busca evitar.

- [x] El `worker_id` proviene de configuración estable; dos arranques consecutivos producen el mismo id y reutilizan la misma fila en `workers`. (`config.py:39` → `WORKER_ID` requerido, sin default)

**Ajuste a T3.8 — "volver a pending" usa el monitor de heartbeat, no un endpoint propio:**

No existe ningún endpoint worker-facing que devuelva un job a `pending`. Las únicas transiciones a `pending` son server-side: `RequeueTimedOutJob` (`jobs/store.go:283`, lo llama el monitor de heartbeat al vencer los 90s) y el retry dentro de `Complete` (`jobs/store.go:218`, solo ante `status="error"` y consumiendo un reintento). Por lo tanto el graceful shutdown de T3.8 **no debe asumir una llamada explícita de "return to pending"**:

- En SIGTERM, terminar el job en curso si alcanza a hacerlo; si no, **salir limpio y dejar de hacer heartbeat** → el monitor de F1 re-encola el job a `pending` en ≤90s (mismo mecanismo que verifica T3.12 al matar el contenedor mid-job).
- **No** usar `Complete` con error para forzar el requeue (gasta un retry y marca el job como error — semántica incorrecta para un apagado limpio).

- [x] T3.8 no llama a ningún endpoint inexistente; el requeue ocurre por timeout de heartbeat (latencia ≤90s), documentado como el comportamiento esperado del shutdown.
